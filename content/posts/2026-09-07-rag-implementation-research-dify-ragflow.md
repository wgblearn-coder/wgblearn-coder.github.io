企业 RAG 落地，最容易出现的误判是：上传文档、连上向量库、让模型回答，就认为系统已经可用。真正困难的是让正确版本的证据，在正确权限范围内稳定进入上下文，并能解释每一次漏召回、错排序和无依据回答。

下面以餐饮 SaaS 的多租户知识库为场景，参考 Dify、RAGFlow 的公开实现，拆开从文档接入到回答评估的全过程。每个节点都回答三件事：它负责什么，为什么这样实现，怎样用实验决定组件和参数。

资料核查日期为 2026 年 9 月 7 日。**产品机制依据官方文档、模型卡与源码；架构、参数和验收门槛是本文提出的 PoC 方案，并非已完成的实测结果。**本文没有部署这些产品或执行模型、数据库性能基准。正式选型需要补齐具体版本、硬件与业务数据测试。

## 一、先定义问题和边界

### 先用一个问题定义系统的工作

假设店长问：“上海门店，外卖订单已经核销，顾客要求退款，谁审批？新制度什么时候生效？”

系统需要联合找到退款制度、区域补充规则和审批权限表，还要排除其他租户的制度以及已经失效的旧版本。用户如果追问“那这笔订单现在退款了吗”，就应转向受控业务 API 查询，不能从制度文档猜测实时状态。

| 问题类型 | 处理方式 | 调研重点 |
| --- | --- | --- |
| 制度、手册、故障处理方法 | 文档 RAG | 证据召回、版本、生效日期与引用 |
| 单笔订单当前状态 | 鉴权后的业务 API | 参数校验、权限、幂等与审计 |
| 上周退款率和门店排名 | 受控 SQL 或指标服务 | 口径、数据权限、聚合准确性 |
| 多份制度之间的差异 | 多文档检索与比较 | 必需证据是否齐全、冲突处理 |
| 知识库没有依据的问题 | 澄清、拒答或转人工 | 不把模型常识当内部制度 |

RAG 的基本思路是把外部检索结果作为生成条件。它不会自动把文档“训练进模型”，也不会天然保证事实正确。原始论文还讨论了检索器与生成器训练；企业工程中的检索、上下文拼接和调用模型，是更广泛的实际用法。[RAG 原始论文](https://arxiv.org/abs/2005.11401)

### 完整链路应拆成三个闭环

```text
离线入库：
数据源 → 接入与版本识别 → 解析/OCR → 清洗与结构恢复
      → 切片 → Embedding → 全文/向量索引 → 校验 → 版本发布

在线问答：
身份与权限 → 意图/路由 → 查询改写与条件提取
          → 带过滤的全文召回 + 向量召回 → 融合去重
          → Reranker → 上下文组装 → 生成 → 引用/拒答校验

持续治理：
请求日志与反馈 → 故障归因 → 冻结评测集 → 消融与回归
              → 灰度发布/回滚 → 数据更新与权限撤销
```

这里“先过滤”指的是**授权条件必须约束候选与数据暴露范围**，不是要求每种数据库都采用同一种物理执行计划。引擎可能先过滤、边遍历边过滤，或者内部过采样再过滤；业务层必须保证未授权正文不进入重排、模型、缓存和用户日志。

### Dify 与 RAGFlow 放在同一张对照表里

本次选取 Dify `1.17.0` 与 RAGFlow `v0.25.6` 作为源码参照，不声称它们是最新版本。产品文档描述能力，固定 tag 源码用于核对实现；PoC 还必须记录镜像 digest、插件和模型版本。

| 环节 | Dify 调研入口 | RAGFlow 调研入口 | 需要验证的实际差异 |
| --- | --- | --- | --- |
| 产品组织 | Workflow、Knowledge Pipeline、知识检索节点 | Dataset、Document、Chunk 与解析/检索配置 | 谁负责入库，谁负责应用编排 |
| 接入与解析 | 数据源、解析和转换节点及插件 | 按格式分派解析器，DeepDoc 等路径 | 图片、表格、扫描件是否保留结构 |
| 切片与索引 | 索引处理器与切片模式 | 文档类型相关解析与 tokenize_chunks | 原文边界、父子关系、索引字段 |
| 召回 | 经济/高质量索引、检索方法及后端适配 | 文本与 dense 检索表达式、文档引擎 | “全文”“混合”到底执行什么 |
| 精排 | 后处理、加权或模型重排配置 | 内部相似度重算或模型重排分支 | 最终分数是否还组合词项/特征 |
| 生成与引用 | 检索结果进入应用上下文并附引用信息 | 检索片段、页码等 reference 进入回答链 | 引用是否真正支撑结论 |
| 工程集成 | 应用编排与模型插件适配 | 文档处理与检索能力对接 | 权限、更新、失败恢复与二次开发 |

Dify 的 Knowledge Pipeline 把数据源、解析、增强、切片、Embedding 和写入组织为可观察节点，并提供 General、Parent-Child、Q&A 等处理路线。这适合研究如何把 RAG 配置与应用流程连在一起；效果仍取决于实际插件与数据。[Dify Knowledge Pipeline 官方介绍](https://dify.ai/blog/introducing-knowledge-pipeline)

固定版 Dify 的检索配置进入 `retrieval_service.py` 后，按 keyword、semantic 或 hybrid 分派；混合候选再进入后处理。阅读顺序应从检索服务到后处理器，再看具体向量后端。[Dify retrieval_service.py](https://github.com/langgenius/dify/blob/09a855dcef24c0edc7431c46c0cfaa494481daf5/api/core/rag/datasource/retrieval_service.py)

其 `weight_rerank.py` 中，加权路径组合向量分数和关键词分数；关键词部分使用关键词提取及 TF-IDF 表示等逻辑，不能一律称为“对原始 BM25 分数加权”。模型重排是另一条路径，调研时应分别记录配置和输出。[Dify weight_rerank.py](https://github.com/langgenius/dify/blob/09a855dcef24c0edc7431c46c0cfaa494481daf5/api/core/rag/rerank/weight_rerank.py)

索引处理器则提供切片规则和 NodeParser 入口，`max_tokens`、`chunk_overlap` 等参数要结合 tokenizer 与具体模式核查。这里值得学习的是处理步骤的可替换接口，而不是复制默认数值。[Dify index_processor_base.py](https://github.com/langgenius/dify/blob/09a855dcef24c0edc7431c46c0cfaa494481daf5/api/core/rag/index_processor/index_processor_base.py)

RAGFlow 的 `rag/app/naive.py` 按格式和配置分派解析器，保留文本/表格等中间结果后再切分和 token 化。研究它时，应从解析后的中间产物一路追到 chunk，不能只看上传界面。[固定版 naive.py](https://github.com/infiniflow/ragflow/blob/8f0632c/rag/app/naive.py)、[DeepDoc 说明](https://github.com/infiniflow/ragflow/blob/8f0632c/deepdoc/README_zh.md)

更关键的是，本次源码的 `rag/nlp/search.py` 在有向量的搜索分支构造文本与 dense 表达式，并使用 `weighted_sum` 融合；它不是本文后面建议的通用 RRF 基线。其 `rerank_by_model` 也会组合词项相似度、模型相关性分数与 rank feature。因此“打开模型重排”不等于最终只按模型分数排序。[固定版 search.py](https://github.com/infiniflow/ragflow/blob/8f0632c/rag/nlp/search.py)

建议 PoC 导出每路原始分数、后处理分数和最终排名。产品参数同名不代表数学意义一致；比较时应固定候选并核对最终评分函数，避免把默认权重差异误认为模型能力差异。

部署也要区分：Dify 的 Compose 涉及应用、Worker、数据库、Redis、插件/沙箱和可选向量后端；RAGFlow 需结合 Compose 的基础服务，核查关系库、缓存、对象存储和选中的文档引擎。不能从一个前端容器成功启动就判断整条 RAG 已可用。[Dify Compose](https://github.com/langgenius/dify/blob/1.17.0/docker/docker-compose.yaml)、[RAGFlow Compose](https://github.com/infiniflow/ragflow/blob/v0.25.6/docker/docker-compose.yml)

对于本文的多客户 SaaS 场景，Dify 1.17.0 的修改版 Apache 许可明确包含多租户运行与前端标识条件，其中 tenant 按 Workspace 定义，应先明确使用形态是否满足授权条件。RAGFlow 仓库采用 Apache-2.0，但模型、解析器和镜像依赖仍需分别记录。[Dify 固定版许可](https://github.com/langgenius/dify/blob/1.17.0/LICENSE)、[RAGFlow 固定版许可](https://github.com/infiniflow/ragflow/blob/v0.25.6/LICENSE)

把 Dify 作为应用编排参照、RAGFlow 作为文档检索参照，是本文的研究分工建议，不代表二者能力互斥。本文后续提出的版本发布、细粒度 ACL 和缓存策略，也不能自动视为这两个产品的默认实现。

### 调研前先收集七类真实约束

不要先给出“百万文档就用某数据库”的结论。文件数不等于片段数，片段数也不能独立决定负载。

| 约束 | 必填数据 | 它影响什么 |
| --- | --- | --- |
| 语料 | 文件格式占比、页数、语言、表格/扫描件比例 | 解析器与 OCR 成本 |
| 规模 | 当前/一年后 chunk 数、每天增删改数量 | 索引、存储、重建时间 |
| 请求 | 峰值 QPS、并发、问题长度与类型占比 | 召回容量、模型批处理 |
| 权限 | 租户数、组数、每人可见比例、撤权时限 | 过滤索引、隔离与缓存 |
| 质量 | 必须答对的业务、错误代价、允许拒答比例 | 评测集和发布门槛 |
| 环境 | CPU/GPU、内存、网络、已有中间件 | 自部署/API 与运维复杂度 |
| 团队 | 搜索、数据库、模型服务的维护能力 | 组件数量与实际总成本 |

没有业务实数时，先以 10 万、100 万 chunk 和 1/10/30 QPS 建立实验档位。这些是测试规模，不能据此宣称生产容量。

## 二、离线入库：把文件变成可追溯证据

### 节点 1：先让每份文档有稳定身份

接入层首先建立“源文档身份”，再考虑模型。建议统一保存 `tenant_id、source_id、doc_id、source_revision、content_hash、acl_version、updated_at`，原始文件放对象存储，元数据放事务数据库。

`source_id` 标识来源位置，`content_hash` 识别内容变化，`source_revision` 标识源系统版本。不同租户上传相同内容，不能因为 hash 相同就共享访问权限；可复用计算结果，但权限关系必须独立。

一条可追踪的流程是：拉取或接收事件，保存原文件，写入导入任务，异步解析，保存阶段产物，最后建索引。至少一次投递下，幂等键要包含租户、文档、版本和流水线版本，否则重试很容易制造重复 chunk。

验证这段流程时，重复发送同一个更新事件，最终应只有一个有效版本；乱序发送旧事件不能覆盖新版本；删除源文件后，还要分别记录全文、向量、缓存与引用预览何时失效。

### 节点 2：先恢复结构，再决定是否 OCR

有文字层的 PDF 应先尝试原生提取，扫描页再 OCR；DOCX、HTML、Markdown 应优先读取标题、段落、列表、表格的原生结构。混合 PDF 需要按页甚至区域决定是否 OCR，避免把本来正确的文字重新识别错。

传统 OCR 常拆成文本区域检测、方向/图像校正和文字识别。文档解析还需要版面分析、阅读顺序恢复、表格结构识别。识别出所有字，并不代表能知道某个金额属于哪一列。

| 候选路线 | 适合的材料 | 原理与实现重点 | PoC 应观察的失败 |
| --- | --- | --- | --- |
| 原生文本/结构解析 | Markdown、HTML、DOCX、文字 PDF | 读取结构树或文字坐标，保留层级 | 多栏顺序错乱、页眉混入正文 |
| Docling | 需要统一文档结构的多格式语料 | 结构化文档表示，记录层级、表格、坐标和来源 | 中文特殊版面、跨页表格需实测 |
| PaddleOCR PP-StructureV3 | 中文扫描件、结构复杂的页面 | 版面检测、OCR、表格等模块组合 | 低清扫描、印章遮挡、合并单元格 |
| RAGFlow 文档解析链 | 想验证产品内解析到引用的闭环 | 检查 DeepDoc 与实际选用解析器 | 不同解析配置是否丢失坐标/表头 |
| 视觉语言模型补充 | 图表、复杂图文关系 | 图像条件下生成结构化结果 | 幻觉文字、遗漏、调用成本 |

Docling 的文档表示可以保存正文层级、表格、图片、边界框和来源信息；PP-StructureV3 则公开了版面检测、OCR、表格、公式等模块化流水线。前者是统一表示的重要参照，后者适合研究中文文档解析模块如何组合。[Docling 文档结构](https://docling-project.github.io/docling/concepts/docling_document/)、[PP-StructureV3 官方说明](https://github.com/PaddlePaddle/PaddleOCR/blob/main/docs/version3.x/pipeline_usage/PP-StructureV3.md)

建议准备 100 页人工标注样本，覆盖文字、扫描、两栏、跨页表格、图片和混合语言。分别评价字符错误率、阅读顺序、表头与数据对应、关键数值准确率及每页耗时；不能只看导出的 Markdown 是否“像一篇文章”。

### 节点 3：清洗后仍要保留原文映射

清洗的目标是减少检索噪声，同时保留决定业务语义的内容。删除重复页眉页脚、修复断行、统一可安全归一化的字符；保留金额单位、否定词、适用条件、例外条款与生效日期。

建议产出统一的 Block：`block_id、type、text、heading_path、page、bbox、table_id、source_revision`。清洗后的文本和原始块之间保留映射，后续引用才能回到页码或坐标。

例如“超过 500 元需要区域经理审批，节假日另有规定”，不能只留下“500 元、区域经理”。清洗一旦丢掉比较关系和例外，即使检索精准，最终答案也会错。

清洗质量可以用至少 30 个业务句子来核对，句子应覆盖“不、除外、大于、有效期、百分比”等条件，并逐条比较原文与清洗结果是否保持完整逻辑。

### 节点 4：切片决定检索和证据粒度

切片影响三个不同目标：召回时是否容易命中，排序时是否容易判断相关，回答时是否具备完整条件。一个固定长度通常无法同时最优。

| 策略 | 具体实现 | 优点 | 风险和适用范围 |
| --- | --- | --- | --- |
| 固定 token 窗口 | 按 tokenizer 限长，设置 overlap | 简单，可作基线 | 条款可能被截断；不能按字符冒充 token |
| 结构切片 | 标题→段落→句子，过长再拆 | 保留制度边界 | 原始结构差时效果受限 |
| 父子切片 | 小子块索引，命中后取父段 | 搜索精准，回答完整 | 父块过大稀释上下文，需去重 |
| 语义切片 | 句向量相似度变化处切分 | 可适配长篇连续文本 | 增加入库计算，阈值不通用 |
| 表格切片 | 每组行重复表头、单位和条件 | 行与列语义完整 | 不能把每个单元格当独立证据 |
| 问答切片 | 常见问题与答案成对保存 | 适合客服 FAQ | 合成问题有偏差，不能代替原证据 |

建议先比较 256/512/768 token 三档子块，overlap 比较 0/64/128，并遵循标题和条款边界。父块试验 1000–2000 token，同时限制最终上下文。参数是实验起点，不能解释为 Dify 或 RAGFlow 的默认值。

对于退款表，索引文本可以是“适用区域：上海；订单：已核销；金额：超过 500 元；审批：区域经理；生效：2026-08-01”。同时保留原表格行和坐标。加入的标题、表头是检索辅助内容，不能冒充原文新增事实。

切片对比要看必需证据的 Recall@K、最终答案条件完整率和上下文 token，平均 chunk 长度只能作为辅助信息。金标准应绑定原文证据范围，不能绑定只在某个切片方案中存在的 chunk ID。

### 节点 5：Embedding 如何把文字变成可搜索向量

Embedding 模型把文本映射为固定维数向量。训练常使用相关的查询—文档作为正样本、其他文档作为负样本，使相关对更接近。其目标是学会任务相关的语义距离，而不是给每个词分配一个可以直接解读的业务坐标。

概念上，一种对比学习目标是提高正样本相对于负样本的相似度：`loss = -log(exp(sim(q,d+)/τ) / Σ exp(sim(q,dj)/τ))`。温度 τ 影响分布尖锐程度。这里只说明常见原理，不代表所有候选采用完全相同的训练目标。

查询和文档可以分别编码，因此文档向量能离线计算；在线只算一个查询向量。文档是“已核销订单撤销办法”，用户问“券用过了还能退吗”，即使没有同词，也可能被向量召回。

| 候选 | 已核实特点 | 作为哪种实验基线 |
| --- | --- | --- |
| BGE-M3 | 1024 维、最长 8192 token；提供 dense、sparse、multi-vector 能力 | 中文/多语言检索及多种表示对照 |
| Qwen3-Embedding-0.6B | 最长 32K，输出最高 1024 维，可调整维数 | 较小参数量候选，测试指令与降维 |
| Qwen3-Embedding-4B/8B | 同系列更大模型，最高维数分别为 2560/4096 | 只有质量收益需要时再进入复测 |
| 托管 Embedding API | 以具体供应商、模型版本、合同为准 | 对比调用成本、网络延迟与数据边界 |

规格来自模型卡，长输入上限不表示应该把整份手册压成一个向量，也不说明更大模型一定适合当前业务。[BGE-M3 模型卡](https://huggingface.co/BAAI/bge-m3)、[Qwen3 Embedding 模型卡](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B)

实现必须固定模型 revision、tokenizer、pooling、归一化方式和查询指令。索引与查询的向量需要处于同一个兼容表示空间；更换模型不能只改查询服务，即使维数相同也需要重建并切换索引。

Embedding 缓存键建议包含 `model_revision + preprocessing_version + text_hash`，涉及租户内容时再明确隔离与访问边界。批量推理使用 token 数控制批次，不只按文本条数；超长文本和失败批次必须可重试、可定位。

### 节点 6：建索引与版本发布

推荐把“文件解析完成”和“知识可供查询”拆成不同状态：`RECEIVED → PARSED → CHUNKED → EMBEDDED → INDEXED → VERIFIED → PUBLISHED`，失败记录所在阶段和原因。

同一批 chunk 同时进入全文和向量索引，使用统一的 `chunk_id、doc_revision、index_generation`。检查文档数、chunk 数、抽样内容、维数、权限字段与查询可见性，再发布 generation。

当两套引擎没有跨系统事务时，不要把两次写入成功当成原子发布。建议先建不可变新代索引，校验后更新一个受控的活动版本指针；查询固定读取同一代。保留旧代用于回滚，失败任务补偿或重放。

可以人为让全文写入成功而向量写入失败，确认查询不会把半发布版本当成完整知识；重建期间请求仍能访问旧版，切换后新请求才读取新代。

## 三、向量数据库：距离计算之外的工程选择

### 距离函数与 ANN 解决的是两件事

余弦相似度是 `dot(q,d) / (norm(q) × norm(d))`，比较向量方向；点积还受向量模长影响；L2 衡量欧氏距离。若两边均单位归一化，余弦与点积排序相同，且 `L2² = 2 - 2×cosine`。

因此必须按模型推荐设置选择距离，而不是随意修改数据库 metric。归一化、量化和模型变化后，分数分布可能变化；“相似度 0.8 就相关”没有跨模型的普遍意义。

精确检索对 N 个 d 维向量逐一计算，粗略计算量为 O(Nd)。ANN 是近似近邻检索，通过少检查一部分向量换速度；它可能漏掉按该向量距离定义的最近邻。

**ANN Recall@K** 比较近似结果和精确近邻；**业务 Recall@K** 比较结果和人工标注证据。前者高只能说明索引近似损失小，不能证明 Embedding 理解对了问题。

### HNSW、IVF 与量化的底层取舍

| 方法 | 怎么搜索 | 主要参数 | 付出的代价 |
| --- | --- | --- | --- |
| Flat 精确扫描 | 对全部候选算距离 | 批次、设备、过滤范围 | 大集合耗时，但适合小集合及真值基线 |
| HNSW | 从稀疏上层图找入口，下沉到稠密底层扩展邻居 | M、efConstruction、efSearch | 图边内存、构建成本、更新维护 |
| IVF | 先找到相近聚类中心，再扫描选中的桶 | nlist、nprobe | 训练与数据分布敏感，漏桶会漏召回 |
| PQ/标量量化 | 压缩向量，用近似值计算距离 | 子空间、码本、位宽、重评分 | 存储下降但可能损失排序精度 |
| 磁盘型 ANN | 把部分索引或向量放磁盘，控制 IO | 缓存、搜索预算、设备 | 内存下降，延迟依赖磁盘与访问局部性 |

HNSW 可以类比先走城市主干道，再进入街道寻找目标。增大 `efSearch` 通常会探索更多候选，倾向于提高召回并增加延迟；它不是业务 TopK。M 影响图连边和内存，构建参数影响索引质量。[HNSW 原始论文](https://arxiv.org/abs/1603.09320)

IVF 的桶由向量聚类形成，不等于租户分区，也不等于数据库分片。PQ 则把向量拆成多个子空间，每段用码本编号近似表示。实际收益应以同一业务召回水平下的内存和延迟比较。

这些是算法类别，不代表每家产品都支持全部方法。正式测试要锁定引擎、索引类型和版本，避免把一个产品的新能力投射到所有版本。

### 六类数据库的横向比较

下表比较的是能力与工程取舍，并非速度排名。相同算法在不同分片、过滤、内存和持久化条件下可能有不同表现。

| 组件 | 索引/查询能力 | 推荐进入对照的条件 | 成本与必须验证的边界 |
| --- | --- | --- | --- |
| pgvector | PostgreSQL 内精确检索、HNSW、IVFFlat，可结合 SQL/事务/关系表 | 已有 PostgreSQL，需要文档与业务权限关联 | 测强过滤后的候选不足、数据库资源争用与备份恢复 |
| Qdrant | dense/sparse、named vectors、payload 过滤、多阶段 Query API | 需要独立向量服务和组合检索接口 | 过滤字段建索引；测试副本、更新可见性及恢复 |
| Milvus | 多种 ANN、多向量/稀疏与标量过滤；集群架构 | 向量负载需要独立扩展，团队能维护集群 | 部署形态和依赖按版本锁定；测试索引构建与写入可见性 |
| Elasticsearch | Lucene 全文搜索加向量 kNN，可组合混合检索 | 已有 ES，重视全文、过滤、聚合和搜索分析 | 分片、内存、向量索引和功能许可要一起评估 |
| OpenSearch | BM25、向量查询与 hybrid search pipeline | 已有搜索运维，想统一词法与向量入口 | 插件/引擎版本兼容，归一化和排名融合配置不能混淆 |
| Weaviate | 对象模型、向量、BM25F 与 hybrid API | 接受其对象/集合模型，期望较高层检索接口 | 测字段 tokenization、融合方式、多租户生命周期 |

事实依据：[pgvector README](https://github.com/pgvector/pgvector)、[Qdrant 查询接口](https://qdrant.tech/documentation/search/hybrid-queries/)、[Milvus 架构](https://milvus.io/docs/v2.5.x/architecture_overview.md)、[Elasticsearch RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion)、[OpenSearch RRF](https://docs.opensearch.org/latest/vector-search/ai-search/hybrid-search/rrf/)、[Weaviate Hybrid](https://docs.weaviate.io/weaviate/search/hybrid)。Milvus 架构链接为 2.5.x，其他滚动文档不构成统一版本基准；PoC 必须保存各自部署版本。

一个容易遗漏的兼容问题是维数：本次查阅的 pgvector README 中，HNSW 的 vector 索引上限是 2000 维，halfvec 为 4000 维。Qwen3 大模型的完整维数不能一律直接套用；需要选择模型支持的较低维输出、不同索引表示或其他引擎，并重新评价召回。存储列能存某维数，不等于对应 ANN 索引支持。[pgvector HNSW 类型限制](https://github.com/pgvector/pgvector#hnsw)

许可也应列入对照：pgvector 使用 PostgreSQL License；Qdrant、Milvus 和 OpenSearch 的核心仓库采用 Apache-2.0；Weaviate 核心仓库为 BSD-3-Clause。Elasticsearch 必须按具体源码部分、发行版与功能核对，不能把所有下载包都称为 Apache 开源软件。[pgvector 许可](https://github.com/pgvector/pgvector/blob/master/LICENSE)、[Qdrant](https://github.com/qdrant/qdrant/blob/master/LICENSE)、[Milvus](https://github.com/milvus-io/milvus/blob/master/LICENSE)、[OpenSearch](https://github.com/opensearch-project/OpenSearch/blob/main/LICENSE.txt)、[Weaviate](https://github.com/weaviate/weaviate/blob/main/LICENSE)、[Elasticsearch](https://github.com/elastic/elasticsearch/blob/main/LICENSE.txt)

**第一轮不必部署六个产品。**已有 PostgreSQL 的团队先测 pgvector 与 Qdrant；已有全文搜索团队先测现有 ES/OpenSearch 与一个向量专用方案；复杂集群扩展或对象模型需求明确后，再纳入 Milvus/Weaviate。这是降低实验成本的建议，不是功能强弱排序。

### 容量估算应从 chunk 开始

若有 100 万个 1024 维 FP32 向量，原始向量空间是 `1,000,000 × 1024 × 4 = 4.096 GB`，约 3.81 GiB。这只是向量数组，不包含图索引、正文、元数据、全文倒排、WAL、缓存、副本和重建临时空间。

设实测每 chunk 的全部索引与元数据空间为 B，副本份数为 R，则长期空间近似 `N × B × R`；重建期还要计入旧、新索引并存和日志增长。不能给原始向量大小随意乘一个系数就宣布硬件足够。

压力测试至少包含冷缓存、热缓存、后台入库、删除更新、索引重建和单节点故障。只测空闲机器的单次 Top10，无法预测午高峰门店同时问答的 P95。

### 真实负载往往先考验过滤

假设用户只能看全库 1% 的文档。如果先拿全库 Top50 再在应用层过滤，可能一个可见结果也没有；把 TopK 加大只能缓解，不能提供稳定保证。

实验应固定数据和查询，分别测试可见比例 100%、10%、1%、0.1%，以及租户等值过滤、ACL 多组过滤、时间范围组合。记录返回不足 K 的比例、业务召回率、P95 和扫描量。

高隔离需求可以使用独立索引、数据库或实例，但会增加资源和管理成本。共享集合可以降低资源浪费，却需要可信身份绑定、强制过滤和缓存隔离；两种方案都不能只靠客户端传入的 tenant_id。

## 四、全文检索与混合召回：把精确词和语义组合起来

### 倒排索引为什么适合编号、术语和条件

倒排索引维护“词项 → 出现这个词的文档列表”。查询“退款 审批”时，系统可以直接访问两个倒排列表，进行交并集和排序，不必扫描全部正文。词位置还可用于短语匹配。

向量擅长“说法不同但意思相近”；全文擅长制度编号、SKU、错误码和专有术语。`E1042` 与 `E1043` 在语义上很像，业务上却可能代表不同故障，所以要保留精确字段。

建议每个 chunk 同时提供 `body_text、title_text、heading_text、business_codes、tenant_id、acl_groups、effective_from、effective_to、generation`。需要分词的是 text 字段；租户、编号、版本通常使用精确匹配类型。

### BM25 的词频、稀有度和长度归一化

常见形式为：`BM25(q,d) = Σ IDF(t) × f(t,d)(k1+1) / [f(t,d)+k1(1-b+b×len(d)/avgdl)]`，求和范围是查询词项。不同实现可能采用不同 IDF 细节。

其中 f 是词在文档中的频次，IDF 让少见词更有区分度，k1 控制词频收益饱和，b 控制文档长度惩罚。直观上，“退款”出现第十次不应比第一次多贡献十倍，而长文也不应只因字多就占优势。

Elasticsearch 默认 BM25 的 k1 为 1.2、b 为 0.75，但这是该实现的默认配置，不是所有语料的最优值。短条款、长手册和带标题的 chunk 应分别测试。[Elasticsearch Similarity 官方文档](https://www.elastic.co/docs/reference/elasticsearch/index-settings/similarity)

### 中文分词必须单独验收

“反结账”“核销”“退菜”“挂账”需要合适的领域词典；中英文混排、连字符、型号和大小写也要检查。索引和查询分析链不一致，会出现正文有词却检索不到。

测试步骤是先查看分析器 token 输出，再执行查询并检查 explain 或等价打分解释。用至少 50 个专有词及编号覆盖同义词、错别字、短语和前缀。不要只看最终模型能否靠猜测答对。

同义词也有范围：“撤销核销”和“退款”并非所有业务下等价。扩展词典应按领域审批并版本化，修改后评估是否需要重建索引。

### 全文检索引擎横向选择

| 方案 | 词法与排序能力 | 中文/业务适配 | 选择理由与限制 |
| --- | --- | --- | --- |
| Elasticsearch | 倒排、BM25、字段权重、短语与复杂查询 | analyzer、词典、同义词；插件版本需匹配 | 全文能力要求高且已有运维基础时优先对照 |
| OpenSearch | BM25、全文查询、hybrid pipeline | 同样需要验证中文分析器及插件 | 搜索一体化候选，不能假设所有 ES 配置直接兼容 |
| PostgreSQL FTS | tsvector/tsquery、GIN、ts_rank/ts_rank_cd | 中文需另外验证分词与词典方案 | 可减少中间件；原生排名函数不能写成 BM25 |
| Weaviate BM25F | 多字段关键词排序并与向量融合 | tokenization、字段 boost、停用词 | 希望全文与对象向量接口统一时对照 |
| Milvus 内置全文路线 | analyzer 与 BM25 Function 生成稀疏表示 | 核对目标版本分析器与中文配置 | 可在向量平台中组合词法检索，须测与搜索引擎差异 |
| Qdrant 全文/稀疏检索 | 当前文档提供 BM25 sparse 推理或客户端生成；文本过滤另算 | 核对语言配置、IDF 与 sparse 生成方式 | 可统一向量和词法路线；需验证目标部署版本支持 |

PostgreSQL 官方定义了 tsvector/tsquery、排序函数与 GIN 使用方法；Milvus 的当前全文文档提供了 BM25 Function 流程。两者都不能仅凭“支持全文”就认定具有相同排序行为。[PostgreSQL 文本查询](https://www.postgresql.org/docs/current/textsearch-controls.html)、[GIN 文本索引](https://www.postgresql.org/docs/16/textsearch-indexes.html)、[Milvus 全文检索](https://milvus.io/docs/full-text-search.md)

Qdrant 当前全文文档明确提供基于 sparse vectors 的 BM25 路线，不能简单描述为“只支持文本过滤”。其文本过滤与有相关性排序的全文搜索仍应区分，中文还需调整语言处理配置。[Qdrant Full-Text Search](https://qdrant.tech/documentation/search/text-search/full-text-search/)

第一轮中文场景建议保留 ES/OpenSearch 作为成熟词法搜索对照，再判断是否值得为了更少服务使用数据库内置词法能力。如果采用 PostgreSQL FTS 或 sparse 方案，报告应明确它与 BM25 基线的实际差异，而不把名称统一改成“全文检索”。

### RRF 与加权分数融合不是一回事

建议的通用基线是：同一权限范围内，BM25 Top50 与向量 Top50 并行召回，按版本化 chunk ID 去重，再做 RRF。参数均为待测试建议。

RRF 只使用排名：`score(d) = Σ wi / (k + rank_i(d))`。排名从 1 开始，缺失于某路的文档在该路不贡献分数。k 常以 60 作为实验起点，它是平滑常数，不是召回数量。

例如 A 在全文排 1、向量排 20，B 两路都排 3。等权且 k=60 时，A 得分约 `1/61 + 1/80 = 0.02889`，B 约 `2/63 = 0.03175`，所以 B 排前。它奖励多路共同靠前，但不能证明 B 一定有业务证据。

加权分数融合则类似 `α×normalized_vector + (1-α)×normalized_keyword`。它利用分数差距，却依赖归一化方式；不能直接把 BM25 的 12.5 和 cosine 的 0.8 相加。

原始 RRF 公式与本文手算采用从 1 开始的排名；不同引擎的默认常数和排名起点可能不同，不能把本文的 k=60 直接视为产品默认。[RRF 原始论文](https://cormack.uwaterloo.ca/cormacksigir09-rrf.pdf)

RRF 适合先建立分数尺度不同的基线；加权融合适合有标注数据后调整。还要测某一路挂掉、返回数量不同、同文多块占满榜单的情况。Qdrant 的 Query API 提供多阶段查询及融合能力，应用侧自行融合时也应保留每路排名和原始分数。[Qdrant Hybrid Queries](https://qdrant.tech/documentation/search/hybrid-queries/)

### 稀疏模型与 BM25 的区别

BM25 使用词频和语料统计，不需要神经网络编码。学习型 sparse 检索用模型为词项分配权重，部分方法还进行词项扩展；它虽然可以使用稀疏索引，却不等于传统 BM25。

BGE-M3 同时提供 dense、sparse 和 multi-vector 输出，选择模型时需明确实际使用哪一部分。支持该模型名称的接口，不代表三种输出和相应索引全部接通。[BGE-M3 模型卡](https://huggingface.co/BAAI/bge-m3)

因此调研报告应把“全文 token 匹配”“BM25 排序”“学习型 sparse”“dense+sparse 融合”分别记录，不统一写成模糊的“支持混合检索”。

## 五、在线链路与 Reranker：候选证据怎样变成回答

### 节点 1：身份、查询理解和改写

由服务端身份生成允许的知识库、租户与 ACL 条件。用户输入可以补充业务范围，不能扩大服务端授权范围；模型提取到的过滤条件也必须经过字段白名单、类型校验和权限交集。

“上海门店已经核销的退款谁批”可以生成语义查询，以及 `region=上海、status=已核销` 等条件。但如果文档缺少 region 元数据，盲目硬过滤会漏掉全国通用规则，应区分确定的权限约束和可能需要宽松检索的业务条件。

多轮追问“那超过 500 呢”需要补全前文主体。建议保留原始查询并与改写查询并行对照；改写必须保留数字、日期、否定、产品版本等硬条件。记录原问、改写和命中变化，检测改写造成的查询漂移。

多查询扩展、HyDE 和 Agent 自主检索应在简单基线不足后再试。它们会增加延迟和候选噪声，也可能放大错误假设；合成文档只能辅助召回，不能作为回答证据。

### 节点 2：召回之后，为什么还要重排

双编码器把问题和文档分别压缩为向量，再用一个距离衡量关系。它足够快，可以搜索大库，但压缩可能丢失“超过/不超过”“允许/禁止”“旧版/新版”等细节。

重排器的任务是在一个较小候选集合内，进一步判断问题与每段证据的相关性。它不是再次做一遍同样的向量检索，也不是负责生成最终答案。

传统 Cross-Encoder 把 query 和 passage 放进同一个模型输入，让 token 之间交互后输出相关性分数。因为文档表示依赖当前 query，不能像双编码器那样把全部计算提前离线完成。

对于采用全注意力的模型，注意力计算随输入长度近似二次增长，还叠加层数与隐藏维数成本。实际吞吐取决于架构、推理后端、批次、padding、量化和设备，不能直接从参数量推算服务延迟。

### Reranker 候选和选择顺序

| 候选 | 原理与公开规格 | 适合验证的问题 | 部署与许可边界 |
| --- | --- | --- | --- |
| BGE-reranker-v2-m3 | 多语言成对评分，典型 Cross-Encoder 使用方式 | 中文制度、短中段落，作为本地基线 | 模型卡 Apache-2.0；长度/精度/batch 固定后测 |
| Qwen3-Reranker-0.6B | 因果语言模型，对任务模板中的相关性判断打分；32K 上下文 | 指令化、多语言、长文本与复杂条件 | Apache-2.0；使用官方模板和 yes/no 分数抽取 |
| Qwen3-Reranker-4B/8B | 同系列更大参数候选 | 小模型在困难样本确有不足时 | 测增加的 GPU/延迟是否换来实际质量收益 |
| Jina-reranker-v2-base-multilingual | Cross-Encoder；1024 token，超长滑窗路线 | 多语言与长文切窗对照 | 权重卡为 CC-BY-NC-4.0；商用另核商业渠道 |
| Cohere Rerank API | 托管候选排序服务 | 不维护模型服务、允许外部 API 的场景 | 具体型号、计费、网络和数据处理条件单独锁定 |

来源：[BGE 模型卡](https://huggingface.co/BAAI/bge-reranker-v2-m3)、[Qwen3 Reranker 模型卡](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)、[Jina 模型卡](https://huggingface.co/jinaai/jina-reranker-v2-base-multilingual)、[Cohere 官方概览](https://docs.cohere.com/v2/docs/rerank-overview)。Jina 一行特指 v2 权重，不代表其所有模型或商业 API 使用同一许可。

Qwen3 的示例并不是让模型自由生成一段排序理由：它将 instruction、query、document 送入因果模型，取末位置 yes/no 对应的 logits，在这两个值之间归一化，得到相关性得分。这个输出仍然需要业务校准，不能解释为答案正确概率。[Qwen3 官方评分示例](https://huggingface.co/Qwen/Qwen3-Reranker-0.6B)

实际选择顺序建议是：先确定本地部署或托管 API 的数据边界；再比较 BGE 与 Qwen3-0.6B；看中文、否定、金额和版本题分层指标；最后同时考虑最终答案增益、P95、成本、运维和许可。不要用不同模型卡上的不同数据集分数排一张伪精确榜单。

Embedding 与 Reranker 不必同一品牌，因为后者通常接收原始 query 和文本；但两者的输入长度、语言覆盖和任务要求应兼容。也不要把 BGE-M3 Embedding 与 BGE-reranker-v2-m3 当成同一个模型。

### TopK、截断、阈值和服务实现

建议基线保留融合后的前 40 个 chunk 给重排，重排后挑 6 个左右进入上下文，再比较候选 20/40/80 和最终 4/6/10。召回数量、重排数量和上下文数量是三个不同参数。

重排输入需要保留标题、正文和关键条件；把所有候选拼成长文后截断，会让后面候选根本未参与评分。每对 query-passage 独立计分，按模型的 tokenizer 和模板限制长度。

长文可以用滑窗评分，但简单取最大窗口分数可能偏向长文。应回到命中窗口对应的原文证据，并在长度分层样本上评估。对重排模型使用最长上下文，也要检查延迟是否符合预算。

Reranker 输出常是 logit 或归一化相关性分数，通常不是经过业务校准的“回答正确概率”。切换模型后不能沿用旧阈值；阈值应在验证集上按错误回答与拒答的成本校准。

建议独立部署重排服务，限制并发、设置队列、按 token 动态批处理，记录候选数、实际长度、截断率和 P95。超时可以退回融合排序，但对审批等高风险问题，应按证据完整性决定是否拒答，并记录降级原因。

### 多向量 Late Interaction 是另一条研究路线

ColBERT 类方法分别编码问题和文档的多个 token 向量，打分时常对每个 query token 找最相似 document token 再求和，即 MaxSim。它保留更细粒度的匹配，也允许文档侧离线计算。[ColBERT 原始论文](https://arxiv.org/abs/2004.12832)

代价是每个 chunk 存储多个向量，索引、计算和压缩方式更复杂。它既可参与检索，也可用于候选重排。只有单向量加普通重排遇到明确质量或吞吐瓶颈时，再加入对照实验。

### 节点 3：上下文组装影响证据使用

去重不只是删除相同字符串。同一文档重叠子块、旧新版本、父子段落可能高度重复。建议按文档和原文范围合并，适当限制单文档占比，再补齐相关父段、表头和例外条款。

每段上下文附带稳定证据 ID、文档名、版本、生效日期、页码和可授权访问的来源。模型引用的是这些 ID，服务端再映射到真实来源，不能让模型自己编造 URL。

预算应按生成模型 tokenizer 计算：`可用证据 token = 上下文上限 - 系统指令 - 当前问题 - 保留历史 - 输出预留 - 安全余量`。上限足够大也不意味着塞得越多越好，要测试噪声增加和关键信息位置的影响。

对示例问题，至少需要退款条件、审批角色、区域规则与生效时间。只命中“审批人”一段但缺少适用条件时，不能因相关性分数高就给确定答案。

### 节点 4：生成、引用、拒答和工具边界

提示词应说明任务、证据格式、冲突处理、缺失信息时的行为。引用文档属于待解释的数据，不具有修改系统权限、要求外传资料或指挥工具执行的权力。

生成后检查引用 ID 是否真实存在、是否在本次授权上下文、关键结论是否获得证据支持。引用存在性可以确定性检查；句子与证据是否相互支持通常需要语义评估和抽样人工复核。

建议拒答原因分成“没有证据”“必要条件不全”“版本冲突”“权限范围内不可获得”“检索服务不可用”。用户可见说明应避免泄露其他租户文档是否存在。

如果后续要真正执行退款，需要独立的业务工具权限和操作约束。回答“制度允许退款”不等于获得执行退款授权；这也是文档问答与业务 Agent 的重要接口边界。

## 六、生产工程：把版本、权限和成本管起来

### 推荐的数据契约与服务职责

以下是建议实现，不是两个参考产品的现成接口。

| 组件 | 输入与输出 | 必须承担的职责 |
| --- | --- | --- |
| 接入服务 | 源文件/事件 → 版本化文档任务 | 幂等、来源身份、更新与删除 |
| 解析 Worker | 原文件 → Block 与坐标 | 可重试、质量标记、保留原始证据 |
| 索引 Worker | Block → Chunk、向量、全文索引 | 同代一致、批量写入、校验发布 |
| 检索服务 | Principal、query、generation → 候选 | 强制权限、查询路由、融合与 trace |
| 重排服务 | query、授权候选 → 分数 | 限流、批处理、模型版本、超时 |
| 回答服务 | 问题、证据 → 答案与引用 | token 预算、依据校验、拒答 |
| 评测任务 | 冻结问题与证据 → 指标报告 | 可复现、分层分析、回归 |

最小 Chunk 元数据包括 `tenant_id、kb_id、doc_id、doc_revision、chunk_id、parent_id、source_span、acl_version、embedding_revision、index_generation`。检索结果再附上 `retrieval_channel、rank、raw_score、rerank_score`。

统一 ID 很重要：全文命中了 v2，向量命中了 v1，如果融合只用 doc_id 去重，就可能保留过期资料。缓存、引用和回滚也需要版本身份。

### 用一段接口伪代码明确在线边界

这段控制流伪代码用于标出在线边界；服务函数需要自行实现，也不是 Dify/RAGFlow SDK 的可直接运行示例。

```python
async def answer(request, principal):
    scope = policy.authorized_scope(principal)  # 来自可信身份
    generation = catalog.active_generation(scope)
    plan = planner.route_and_rewrite(request, scope)
    if plan.route == "business_api":
        return await business.read_with_policy(plan, principal)

    constraints = policy.intersect(scope, plan.filters, generation)
    query_vector = await embed(plan.query, generation.embedding_revision)
    lexical, dense = await parallel(
        text_search(plan.query, constraints, limit=50),
        vector_search(query_vector, constraints, limit=50),
    )
    candidates = fuse_and_deduplicate(lexical, dense)
    authorized = policy.recheck(candidates, principal)
    ranked = await rerank(plan.query, authorized[:40])
    context = pack_evidence(ranked, token_budget=request.context_budget)
    if not evidence_is_sufficient(context, plan):
        return refuse_or_clarify(plan)
    result = await generate(plan, context)
    return validate_and_attach_citations(result, context, principal)
```

生产实现还需超时预算、单路失败处理和审计。`evidence_is_sufficient` 也不是一个神奇布尔函数：应由必要条件覆盖、版本一致、分数校准与业务规则组合，并在无答案集上评估。对最终输出做权限复核，是为了覆盖检索期间发生撤权等竞态。

### 权限撤销与缓存如何一起处理

建议回答缓存键包含租户、权限范围摘要、ACL 版本、知识 generation、原问/改写、模型与提示词版本，以及必要的历史会话摘要。只用 query 作为 key 会导致不同用户共享不该共享的回答。

权限撤销优先影响查询可见性，不必等待所有磁盘数据物理清理完成。可先更新权威权限版本并让缓存失效，再异步清理索引与产物。读取原文预览和父块时仍需校验权限，不能认为子块检索通过就永远有效。

**必须测试：**A 租户命中后 B 租户问同题；撤销权限后重复同题；旧会话继续追问；共享链接打开引用；相同文件名/相似租户 ID；后台重建时读取旧缓存。

### 异常处理应该按节点设计

| 故障 | 预期行为 | 需要的证据 |
| --- | --- | --- |
| OCR 部分页失败 | 标记缺页，按政策隔离或明确不完整 | 页码、失败阶段、重试次数 |
| Embedding API 限流 | 退避重试、任务不重复发布 | 幂等键、批次、失败 token 数 |
| 全文/向量单路故障 | 有条件单路降级，记录质量影响 | channel_status、剩余预算 |
| Reranker 超时 | 回到融合排序或拒答 | 候选、耗时、降级原因 |
| 版本发布中断 | 保持上一可用 generation | 当前指针、新代校验状态 |
| 无授权证据 | 澄清或拒答 | 权限内结果数，不暴露他租户内容 |
| LLM 流中断 | 标记答案未完成，避免当成功缓存 | 首 token、结束状态、引用校验状态 |

### 可观测性要找到第一处失败

建议每次请求保留同一 trace_id，依次记录身份校验、查询改写、过滤条件摘要、各路候选 ID 和分数、融合结果、重排前后、最终证据、生成耗时、引用和拒答原因。

日志应按权限保留，正文采取最小化、脱敏或受控采样。在线问题归因的顺序是：源文档是否存在 → 解析是否正确 → 切片是否保留证据 → 权限是否合理 → 召回是否命中 → 重排是否丢掉 → 上下文是否截断 → 模型是否误读。

这条归因链能避免所有错误都被归结为“模型不够强”。如果正确证据根本没有进入候选，换 Reranker 不会凭空找到它。

### 时延和费用应按请求链计算

并行全文与向量时，检索段耗时近似由较慢一路决定，再加融合开销；整条链还要加鉴权、查询理解、Embedding、重排、上下文和生成。不要把各节点 P95 直接相加当作端到端 P95，要用完整 trace 实测。

建议分别报告检索 P95、重排 P95、TTFT、答案完成 P95 和超时率。流式生成改善的是等待感受，不能掩盖检索已经消耗了两秒。

每月总成本包括数据库/搜索、模型服务或 API、对象存储、网络、解析、备份以及维护时间。单问成本还应计入查询改写、重排、长上下文与失败重试；入库成本按更新频率分摊。

选择自部署模型时，按峰值并发和闲置率计算 GPU 成本；选择 API 时，固定价格核查日期、计费单位、限流、数据处理约定。本文不提供未经核实的实时价格。

## 七、可执行的 PoC：数据集、实验矩阵与验收

### 建立 300 题冻结评测集

建议先准备 300 个问题，每题以主类型分桶，同时可带语言、长度、租户和权限等交叉标签。问题来自真实业务人员和工单脱敏样本；模型合成题只能补充覆盖范围。

| 主类型 | 建议题数 | 代表问题 |
| --- | --- | --- |
| 单文直接事实 | 60 | 某角色有何审批额度 |
| 同义表达/口语 | 40 | 券用过了还能不能退 |
| 编号/错误码/精确词 | 40 | E1042 如何处理 |
| 表格、数值、例外与否定 | 50 | 不超过 500 元是否免审批 |
| 多文档组合 | 40 | 全国制度与上海补充条款如何合用 |
| 新旧版本与时效 | 30 | 8 月后的制度是什么 |
| 无答案与权限负例 | 40 | 他租户规则、缺失知识、撤权后查询 |

每题记录参考答案、必需证据范围、可替代证据组、允许访问范围、文档版本、错误后果和是否应该拒答。至少两位业务人员复核有歧义样本，无法达成一致的题单独报告。

可按 150/75/75 划分开发、验证和最终测试集，并按文档/问题家族分组，避免同义改写分别落在训练调参与测试集。所有业务类型尽量分层覆盖；另设不参与调参的权限回归集。

### 指标必须分别评价检索和回答

| 指标 | 定义或观察对象 | 能解释什么 |
| --- | --- | --- |
| Evidence Recall@K | 命中的必需证据单元数 / 全部必需单元数 | 召回是否足够完整 |
| Hit@K | 至少命中一个相关证据的题目比例 | 快速发现完全漏召回，但不能代表多跳完整性 |
| MRR | 第一个相关结果排名倒数的平均值 | 首个证据是否靠前 |
| nDCG@K | 按相关等级与位置折扣后的归一化收益 | 排序整体质量，适合重排比较 |
| 答案正确率 | 业务判断、条件、数值与版本是否正确 | 最终任务是否完成 |
| Faithfulness | 答案断言是否获得提供证据支持 | 是否无依据发挥 |
| 引用准确/覆盖率 | 引用是否支持对应结论、关键结论是否有引用 | 可追溯性质量 |
| 拒答正确率 | 应拒答时拒答、可回答时不过度拒答 | 风险与可用性的平衡 |
| 权限泄露数 | 授权外数据进入下游或可见输出的次数 | 安全边界，不与平均质量相抵消 |
| P50/P95、成本 | 指定负载、输入长度、硬件下统计 | 服务是否可持续运行 |

Ragas 可辅助计算上下文和回答指标，Faithfulness 关注答案断言能否由上下文支持。即使 Faithfulness 高，如果上下文是过期制度，业务答案仍可能错误，因此不能用一个自动分数替代业务验收。[Ragas 指标目录](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/)、[Faithfulness 定义](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)

计算 Recall 时，无答案问题不应分母为零硬算一个数；它们应进入拒答评估。若有多个等价证据，用证据组判定满足，避免把重复表述都算成“必须全部召回”。

### 先分离产品能力和组件能力

产品端到端实验使用同一批原文件，让 Dify 与 RAGFlow 各自完成解析和索引，观察完整体验。组件实验则使用同一批已经冻结的 chunk、Embedding 和过滤条件，才便于比较数据库或重排器。

否则一个产品因为解析漏表头而答错，很容易被误记为“它用的向量数据库不好”。报告必须说明每组实验的可控变量与不可控差异。

| 阶段 | 实验组 | 固定什么 | 输出 |
| --- | --- | --- | --- |
| A 解析 | 原生、Docling、PaddleOCR、产品内解析 | 同一原文件 | 结构/关键字段错误及每页成本 |
| B 切片 | 固定、结构、父子 | 同一解析 Block | 证据完整率、Recall、token |
| C Embedding | BGE-M3、Qwen3 小模型，必要时大模型 | 同一 chunk、精确或高召回检索 | 模型质量与编码成本 |
| D 引擎 | pgvector、Qdrant，按场景增加其他 | 同一向量、相同过滤与硬件预算 | 等召回水平的时延和资源 |
| E 召回 | BM25 only、dense only、RRF、加权融合 | 同一索引和标注 | 各问题类型的增益与回退 |
| F 重排 | 无重排、BGE、Qwen3、候选 API | 冻结同一候选集合 | nDCG、答案正确率、重排耗时 |
| G 生成 | 固定模型，比较上下文数量/布局 | 检索与重排结果 | 正确率、忠实度、token |
| H 端到端 | Dify、RAGFlow、最小自建链 | 同一原始数据与问题 | 可维护性、总成本、完整质量 |

先单因素筛选，再测试最有希望的组合，不运行全部参数笛卡尔积。对照组必须保留“无重排”，才能知道 GPU 或 API 支出是否带来实际收益。

### 重排专项实验应怎样做

先冻结同一批融合 Top80 候选，再分别给重排器 20/40/80 个候选。固定模板、token 限制和精度，记录每种模型截断比例及实际处理的 token 数。

第一轮比较 nDCG@10、必需证据进入最终 Top6 的比例；第二轮在固定生成模型下比较答案正确率。并单列否定、数值、长段落、中英混合和版本冲突等困难样本。

若某模型 nDCG 更高但答案没提升，要检查最终上下文是否已包含足够证据、父块补全是否冲掉排序收益。若正确率提高但 P95 超预算，可缩候选、减输入长度、批处理，最后才决定是否接受更大服务成本。

### 负载、故障和可复现记录

先预热，再在 1/10/30 QPS 档位测试；每档建议至少 15 分钟，或获得足够尾延迟样本后延长。记录实际请求到达率、完成率和排队，避免客户端发送变慢掩盖系统过载。

至少做一次冷启动、持续增量导入、强过滤、热点租户、节点重启、重排超时、撤权和删除传播实验。所有性能数据同时附硬件、索引参数、模型 revision、输入长度和并发条件。

每次实验保存配置、语料摘要 hash、评测集版本、源码 commit、模型 revision、随机种子、原始结果与日志。对生成和自动裁判重复采样，并人工抽查分歧；小样本的一两个百分点不应直接宣布胜负。

### 先定门槛，再做选型评分

以下为待业务确认的**初始门槛**：关键制度题 Evidence Recall@20 ≥ 90%；关键题答案正确率 ≥ 90%；授权外内容泄露数为 0；引用存在性校验通过率为 100%；检索加重排 P95 在约定负载下 ≤ 800 ms。TTFT 与完成耗时需按最终生成模型另立预算。

这里 800 ms 只是预算建议，不是任一产品承诺。权限零泄露是测试集发布门槛，不代表有限测试已经证明所有输入都安全；仍需要实现层面的强制权限约束。

通过硬门槛后，可按质量 35%、延迟/吞吐 20%、运维 15%、成本 15%、集成扩展 10%、可迁移性 5% 加权。每项 1–5 分必须附实验或工作量证据；许可和数据边界不合适的方案直接排除，不靠综合分抵消。

## 八、实施排期、交付物与下一步决策

### 四周调研实施计划

| 时间 | 主责 | 工作 | 可检查的交付物与退出条件 |
| --- | --- | --- | --- |
| 第 1 周 | 业务专家 + 数据/后端 | 约束访谈、原文件抽样、300 题标注、产品版本冻结 | 数据清单、证据集、权限模型、可复现环境 |
| 第 2 周 | 数据/检索工程师 | 解析、切片、Embedding、索引与过滤基线 | 分节点报告，先解决证据丢失 |
| 第 3 周 | 检索/模型工程师 | 混合检索、重排、上下文与生成消融 | 至少两套候选组合和失败案例 |
| 第 4 周 | 后端/SRE + 业务 | 并发、故障、撤权、成本与迁移测试 | 决策记录、灰度方案、回滚与运维手册 |

时间以 2–3 名工程人员和可参与标注的业务专家为假设；如果数据接入、合规或权限系统尚未建立，需要重新估期。角色可以由同一人兼任，不代表已经安排真实人员。

### 每个节点都应提交同一张调研卡

调研卡包含：业务问题、输入输出、底层原理、候选实现、官方证据、固定版本、可变参数、失败模式、实验数据、结论及退出条件。这样后续可以定位为什么选择该方案，而不是只留下组件清单。

交付物至少包括语料与权限清单、黄金问题集、产品/组件差异表、可复现实验配置、逐节点指标、困难样本集、成本模型、部署与回滚说明，并在选型记录里写清放弃某个方案的原因。

### 第一轮应该先验证哪套组合

建议从“结构切片或父子切片 + BGE-M3/Qwen3 小模型对照 + BM25/dense 混合 + BGE/Qwen3 小型重排对照”开始。数据库优先复用团队已有能力，同时保留一个专用向量库候选，以数据说明是否值得新增组件。

产品层分别验证 Dify 的应用编排路径和 RAGFlow 的文档处理/检索路径。只有明确发现某个产品的扩展点、权限边界或版本管理无法满足要求，才评估替换局部检索服务或自建；每个新增组件都需要对应一个可复现的问题。

下一步先拿真实制度、表格和失败问题做测试，确认正确证据究竟在哪一段丢失，再决定是否调整切片、Embedding、检索引擎或 Reranker。最终报告要能回答：在这批数据和这些约束下，哪套链路通过了验收，依据能否复现。
