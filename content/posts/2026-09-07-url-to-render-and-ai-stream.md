在浏览器输入一个网址，几秒后看见页面，这是 Web 开发最适合用来串联知识的一条主线。DNS、TCP、HTTP、缓存、数据库、JavaScript、重排和 GPU 都能放到具体位置上，不必分成彼此无关的名词背诵。

再往前走一步：打开餐饮经营后台，看到营业额，输入“昨天的营业额为什么下降了？”，等待 AI 逐字回答。我们又会遇到鉴权、RAG、工具调用、推理调度、KV Cache、流式协议和前端增量更新。**模型应用复用了 Web 请求的基础链路，并在后端增加生成与编排，在前端增加持续接收与渲染。**

本文使用这个虚构业务场景讲解机制。域名、接口、时延和容量均为教学示例，不代表任何实际系统的生产配置。浏览器内部以 Chromium 为主要参照，进程划分会随版本、平台和隔离策略变化；协议语义与某个浏览器的实现方式需要分开理解。

## 1. 先把整条链路和参与者放到一张地图上

### 页面导航、业务请求和模型请求是三段连续旅程

假设用户访问 `https://ops.example.com/dashboard?store=42#sales`。我们先看三个动作分别做什么。

| 用户动作 | 发出的主要请求 | 服务端返回 | 浏览器接下来做什么 |
| --- | --- | --- | --- |
| 输入网址并回车 | 页面文档导航 | HTML，随后还有 CSS、JS、图片等 | 建立文档并渲染 |
| 页面查询营业额 | `GET /api/sales?store=42` | JSON | 更新状态和 DOM |
| 点击“分析原因” | `POST /api/chat` | 持续到达的事件或文本增量 | 解码、解析、批量更新回答 |

第一段可能是服务端渲染的完整页面，也可能只是单页应用的壳。第二、三段通常不需要重新加载整个文档。客户端路由切换还可能只更新 URL、局部状态和数据，所以“地址变了”不必然意味着完整导航。

可以先记住这条逻辑路径。箭头表示依赖和数据方向，不表示每次都必须串行经过所有节点：

```text
地址栏 / 页面交互
  → 浏览器导航或 Fetch
  → 缓存判断、域名解析、连接复用或建立
  → CDN / 接入代理 / 负载均衡
  → 网关 / 应用服务
  → 缓存、数据库、下游服务
  → HTTP 响应
  → 浏览器解析数据、执行脚本、更新 DOM
  → 样式、布局、绘制、光栅化、合成、屏幕显示

模型请求在应用服务后继续：
  → 会话与权限 → 检索 / 工具 → 提示词
  → 推理排队 → Prefill → Decode
  → 事件流沿网络返回 → 页面持续更新
```

CDN 命中可以省掉回源；新鲜的本地 HTTP 缓存可以省掉资源网络请求；已有连接可以省掉建连；HTML 下载、解析和子资源加载可以重叠。它是一张带分支的依赖图，不能简单把所有名词各算一次再相加。

### 进程与线程：谁负责接收，谁负责画出来

进程拥有受操作系统保护的地址空间与资源，线程是在进程内执行工作的单位，同进程线程通常共享地址空间。浏览器拆成多个进程，是为了隔离故障和权限，同时也会增加内存与通信成本。

| 参与者 | 主要职责 | 在本场景中的动作 |
| --- | --- | --- |
| Browser 进程 | 地址栏、标签页、导航和权限协调 | 接受网址，协调导航提交 |
| Network Service | 网络栈、连接与请求处理 | 获取 HTML，接收 API 数据流 |
| Renderer 进程 | 文档、脚本和渲染相关工作 | 解析页面、运行应用、更新回答 |
| Renderer 主线程 | JS、DOM、样式和布局等 | 处理点击，修改回答节点 |
| 合成线程及光栅任务 | 管理合成、生成可显示内容 | 组织图层与图块，准备帧 |
| GPU / 显示合成相关服务 | 图形资源与帧合成、提交 | 配合系统将结果显示出来 |

这是一张职责表，不是所有平台固定不变的进程清单。一个标签页可能因跨站 iframe 涉及多个 Renderer，多个页面也可能共享进程；“一个标签页等于一个进程”只是简化。隔离概念可参照 [Chrome 多进程架构介绍](https://developer.chrome.com/blog/inside-browser-part1)。该系列发表于 2018 年，本文不沿用其中已经过时的插件进程等示例。

**IPC 是同一台机器上不同进程之间的通信。**它与浏览器通过 HTTP 请求远端服务器是两层事情。Chromium 使用 Mojo 等机制传递接口调用和数据；大数据还可以通过数据管道、共享内存等方式传输，并非所有内容都复制成一条巨大消息。实现边界见 [Chromium Mojo 与服务文档](https://chromium.googlesource.com/chromium/src/+/main/docs/mojo_and_services.md)，Network Service 也可以因配置运行在进程内。

一次导航会发生浏览器与渲染器的协调：选择合适的渲染进程、提交导航、交付响应数据流，随后渲染器推进加载。页面里的 `fetch()` 也需要跨越渲染器与网络服务的边界。JS 回调并不是在网络进程里直接执行。导航交接可参考 [Chrome 导航流程](https://developer.chrome.com/blog/inside-browser-part2)。

## 2. 输入 URL 之后：先理解地址、缓存和 DNS

### URL 中哪些内容会交给服务器

`https://ops.example.com/dashboard?store=42#sales` 可以拆成协议、主机、默认端口 443、路径、查询参数和片段。

普通 HTTP 请求会携带路径 `/dashboard` 和查询参数 `store=42`；`#sales` 片段不随这次 HTTP 请求发送给服务器，通常用于页面内定位或客户端逻辑。主机名参与 DNS、TLS 身份验证以及 HTTP 的主机路由。HTTP/1.1 常用 `Host`，HTTP/2、HTTP/3 使用 `:authority` 等伪首部。

浏览器还需要判断输入是网址还是搜索词，处理 URL 规范化，以及适用的 HTTPS 升级策略。HSTS 可以让浏览器在发出明文 HTTP 请求前改用 HTTPS；服务端 301/302 等重定向则要先收到响应，再发起下一次请求。两者发生的位置不同。

### “浏览器缓存”至少包含五种不同东西

| 类型 | 保存什么 | 命中以后省掉什么 | 不能混淆的边界 |
| --- | --- | --- | --- |
| DNS 缓存 | 名称解析结果 | 重复解析 | 没有保存 HTML 正文 |
| HTTP 缓存 | 响应和相关元数据 | 下载，或通过验证省正文 | 内存/磁盘是存储位置，不是两套 HTTP 语义 |
| Service Worker + Cache Storage | 应用代码管理的请求/响应副本 | 由应用策略决定 | 不自动等同于 HTTP 新鲜度机制 |
| BFCache | 可恢复的页面状态快照 | 后退/前进时重建页面的大量工作 | 与普通资源缓存不同，也不保证每页都能进入 |
| 应用存储 | localStorage、IndexedDB 中的数据 | 应用自行决定 | 不会自动成为 Fetch 的响应缓存 |

缓存还不只有客户端一层：CDN 是共享 HTTP 缓存，Redis 常是服务端业务数据缓存，模型 KV Cache 则保存推理中间状态。讨论“缓存命中”时，必须说清楚命中了哪一层、复用了什么、隔离键是什么。

### 新鲜缓存与条件请求：200 和 304 分别意味着什么

所谓“强缓存”是常见教学术语：浏览器依据 HTTP 缓存规则判断副本仍然新鲜，直接复用，通常不为该资源发送请求。开发者工具可能显示状态 200 和 `from memory cache` / `from disk cache`，并不代表服务器刚返回了一次 200。

缓存需要验证时，可以发送 `If-None-Match` 携带 ETag；也可使用 `If-Modified-Since` 携带上次修改时间。如果表示未变，服务端返回 304，浏览器更新缓存元数据并复用原正文。**304 仍然发生了网络请求，只是没有重新传输该表示的正文。**

以下是三类独立响应的教学配置。带内容哈希的公共静态资源，例如 `app.8f3a.js`，可以采用长时间缓存：

```http
Cache-Control: public, max-age=31536000, immutable
```

HTML 可以保存，但每次复用前要求验证：

```http
Cache-Control: no-cache
ETag: "html-v7"
```

不应存储的敏感响应：

```http
Cache-Control: no-store
```

`no-cache` 允许存储但要求复用前验证；`no-store` 禁止缓存存储；`private` 限制共享缓存存储，却不禁止浏览器私有缓存。

`Vary` 将指定请求头纳入缓存匹配，`s-maxage` 面向共享缓存。认证内容需要专门设计缓存策略，不能仅凭 URL 相同就跨用户复用。语义依据 [MDN HTTP 缓存指南](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching)。

普通刷新、强制刷新、DevTools 禁用缓存、Service Worker 策略会改变实际路径。不要背诵“任何页面必定先查内存，再查磁盘，再做 DNS”的绝对顺序；预连接和导航预加载还可能并行发生。

### DNS：把域名解析为可以连接的目标

当确实需要网络且没有合适的可复用连接时，浏览器需要目标地址。结果可能来自浏览器或系统已有的解析缓存，也可能需要向递归解析器查询。实际解析路径受系统配置、浏览器安全 DNS、代理和企业策略影响。

在没有相关缓存的简化场景里，递归解析器从根服务器取得顶级域的线索，再找到域名的权威服务器，最终取得 A/AAAA 等记录并按 TTL 缓存。**通常是递归解析器逐级寻找答案，不是浏览器亲自依次访问根、顶级域、权威服务器。**CNAME 表示别名，解析还需要继续找到可用地址。

传统 DNS 常使用 UDP，也能使用 TCP；[DoH](https://developers.google.com/speed/public-dns/docs/doh) 把 DNS 查询承载在 HTTPS 上。因此不能说“DNS 永远只用 UDP 53”。DNS 还可能参与 CDN 调度，但解析结果是 IP 等记录，不会把 HTML 返回给浏览器。

一个域名可能解析出多个 IPv4/IPv6 地址，客户端会根据连接策略选择或竞速。TTL 控制缓存有效时间，却不是“修改 DNS 后全世界同时切换”的倒计时；不同缓存和已有连接可能处于不同状态。

### 从 IP 到网卡：补齐真正的数据路径

域名解析完成后，操作系统根据路由表选择出接口与下一跳。在常见以太网或 Wi-Fi 局域网中，IPv4 使用 ARP、IPv6 使用邻居发现获取下一跳链路地址；目的服务器不在本地子网时，下一跳通常是网关，而不是远端服务器的 MAC 地址。

数据经过网卡、接入网络、路由器和运营商网络到达目标。家庭路由器可能执行 NAT，公网中间路由器继续按 IP 转发。DNS 解决名称定位，IP 解决寻址和路由，TCP/QUIC 提供传输能力，HTTP 表达应用请求；分清职责后，分层模型就落到了实际包的路径上。

## 3. 连接与 HTTP：把请求可靠地送到接入层

### HTTP/1.1、HTTP/2 与 HTTP/3 的传输基础

| 协议 | 常见 HTTPS 传输组合 | 复用方式 | 关键限制 |
| --- | --- | --- | --- |
| HTTP/1.1 | TCP + TLS | 持久连接复用，浏览器也使用多个连接 | 同一连接缺少 HTTP/2 式并发多路复用 |
| HTTP/2 | TCP + TLS | 一条连接承载多个 HTTP 流 | TCP 丢包仍可能阻塞多个流的数据交付 |
| HTTP/3 | QUIC，通常承载于 UDP | QUIC 的多个可靠流 | 不同流减少相互等待，但仍共享带宽和拥塞约束 |

HTTP/3 不走 TCP 三次握手。UDP 本身不提供可靠性，但 QUIC 在其上实现可靠传输、拥塞控制和集成的 TLS 握手，所以“用了 UDP 就会随意丢回答”也不成立。HTTP/3 的协议基础见 [RFC 9114](https://www.rfc-editor.org/rfc/rfc9114)。

浏览器先检查能否复用连接；同源并不保证必定复用成功，连接状态、隔离分区和服务端策略都会影响结果。不同域名在满足证书、协议和实现限制时也可能发生连接合并，不能用“一域名一 TCP”描述全部情况。

### TCP 三次握手为什么需要来回确认

以新建 TCP 连接为例，简化过程是：

```text
客户端 → 服务端：SYN，seq=x
服务端 → 客户端：SYN + ACK，seq=y，ack=x+1
客户端 → 服务端：ACK，ack=y+1
```

这用于同步初始序列号、确认双方通信能力并建立连接状态，避免仅凭一个过期连接请求就建立完整连接。TCP 后续通过序列号、确认、重传等提供可靠且有序的字节流。它不认识一条 JSON 的边界，应用协议需要自己分帧。TCP 的连接与可靠传输语义见 [RFC 9293](https://datatracker.ietf.org/doc/html/rfc9293)。

流量控制关注接收端是否来得及接收，拥塞控制关注网络是否承受得住。接收窗口与拥塞窗口约束不同。丢包、往返时延和拥塞都可能让下载变慢，即使服务器处理只用了几毫秒。

关闭连接时，两个方向分别结束，因此经常用“四次挥手”讲解，但 ACK 与 FIN 可以合并，不能把包数写成固定四个。TIME_WAIT 有助于处理末次确认丢失和旧报文，它不是出现就说明系统异常。HTTP 持久连接也不会在每次响应后立即关闭。

### TLS：先验证身份，再保护 HTTP 内容

HTTPS 中，客户端与 TLS 终止点协商加密参数，验证证书链与域名等条件，完成密钥协商，随后加密传输 HTTP 内容。证书用于身份验证，现代 TLS 常用临时密钥交换建立共享秘密，再使用对称加密保护数据，不是“把所有 HTTP 内容都用证书公钥加密”。

TLS 1.3 完整握手通常具有 1-RTT 的握手结构；这不是整次访问只花一个 RTT，TCP 建连、DNS 和服务处理还可能另有耗时。会话恢复、预连接会缩短路径。0-RTT 早期数据有重放风险，不能随意用于下单、扣费等不可重复操作。协议与重放限制见 [RFC 8446](https://datatracker.ietf.org/doc/html/rfc8446)。

ALPN 可协商 HTTP/2 等应用协议；SNI 帮助服务端选择站点证书，域名信息是否被额外保护取决于 ECH 等部署条件。TLS 在 CDN 或负载均衡终止时，客户端加密连接止于该处；接入层到后端的连接需要单独配置保护。

### 请求、响应与跨域发生在哪里

营业额接口可以抽象为下面的 HTTP/1.1 报文。教学示例省略了 Cookie 等身份信息：

```http
GET /api/sales?store=42 HTTP/1.1
Host: ops.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8
Cache-Control: no-store

{"storeId":42,"revenue":12500}
```

同源由协议、主机和端口共同确定。页面请求另一个源的 API 时，浏览器可能根据方法和请求头先发 OPTIONS 预检，也可能直接发实际请求，再限制脚本读取响应。**CORS 不等于服务端鉴权，也不保证请求没有发到服务器。**规则见 [MDN CORS 指南](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS)。

Cookie 是否携带还受 Domain、Path、Secure、SameSite 以及 Fetch 的 credentials 模式等约束；HttpOnly 限制 JS 读取 Cookie。CSRF、XSS 和越权分别涉及跨站请求滥用、脚本注入和权限判断，不能通过“开了 HTTPS”或“配了 CORS”一起解决。

## 4. 后端服务：从接入层走到数据，再返回响应

### CDN、负载均衡、网关各自解决什么

CDN 把可缓存资源放到接近用户的节点；反向代理代替后端接收请求；负载均衡把请求或连接分配给多个实例；网关常承载路由、身份校验、限流和协议处理。这些是职责，同一产品可以承担多个职责，不意味着必须部署四台机器。

例如浏览器先连到 CDN，静态 JS 命中边缘缓存直接返回。业务 API 再转发到负载均衡和应用入口。后端实例不会因为 DNS 查出了 CDN 地址就直接收到浏览器的原始 TCP 连接：代理可能终止前一段连接，再建立或复用后一段连接。

在 Kubernetes 中，可用下面的路径理解，但真实部署可能省略或合并节点：

```text
公网负载均衡
  → Ingress / Gateway 的实际控制器或代理
  → Service 所定义的后端集合
  → 就绪 Pod 中的应用进程
```

Ingress、Gateway 和 Service 首先是配置或逻辑资源。**Service 不是一台额外的机器，也不是必然运行代理进程的一跳。**转发可能由节点数据面规则完成，入口控制器也可能直接选择 Pod 地址。控制面负责维护期望状态，数据面承载真实请求。参考 [Kubernetes Service 文档](https://kubernetes.io/docs/concepts/services-networking/service/)。

### 一个营业额查询如何经过 Java 服务

假设这是 Spring MVC 应用，请求可能先由 Web 容器接收，再经过 Filter、DispatcherServlet、拦截器和 Controller，进入 Service 与数据库访问层。该顺序描述常见 Servlet 应用；响应式框架与其他语言有不同执行模型。

服务先根据登录态确定用户，再检查用户是否能读取门店 42。**参数 `store=42` 是资源选择条件，不是授权证明。**应用缓存键至少要考虑租户、门店、统计时间范围与数据版本；授权不能因为命中缓存就被跳过。

随后可能先查 Redis；未命中时，从数据库连接池取得连接，执行带条件的查询，再把结果写入缓存。索引让数据库减少定位和扫描成本，但复杂聚合是否高效还取决于执行计划、数据分布和统计方案。高频报表可以使用预聚合，代价是新鲜度与维护复杂度。

对更新接口还要考虑事务和并发。数据库事务不能自动覆盖外部支付或消息队列；提交后要可靠发事件，可以使用 Outbox 等方案。MQ 解耦后续工作，但如果用户必须立即得到某个结果，把工作扔进队列并不会自动满足同步响应需求。

### 应用代码没变，接口为什么突然变慢

请求可能消耗时间的位置包括入口排队、线程池、连接池、SQL、锁等待、缓存、下游调用、GC 和序列化。应当把这些等待拆开，而不是看到 CPU 升高就认定是某段业务逻辑慢。

一个算术例子：在稳定状态下，若平均每秒 100 个请求、每个请求平均占用数据库连接 0.2 秒，则平均在用连接约为 `100 × 0.2 = 20`。这不是连接池最终配置，还要考虑突发、时延分布和数据库承载上限；盲目扩大线程池与连接池可能把拥塞推给数据库。

超时、重试、限流和熔断需要一起设计。总请求预算只有 3 秒，就不能让三个下游各自等待 3 秒。重试会放大流量，对结果未知的写请求应先按原幂等键查结果，不能换一个键再写一遍。

### 返回 200 之后，还有哪些事情没有完成

应用把结果序列化成 JSON 或 HTML，设置状态码与响应头，经过压缩、代理和传输返回。服务器写入输出缓冲区成功，不代表浏览器已收到，更不代表页面已显示。

SSR 在服务端生成较完整的 HTML，CSR 主要在客户端取数据并构建页面，SSG 在构建阶段预生成页面。Hydration 是客户端框架把交互能力接到服务端输出的 HTML 上；它仍会消耗下载、解析和执行脚本的时间。首屏能看见，并不代表所有按钮已能及时响应。

## 5. 浏览器渲染：把字节变成屏幕像素

### HTML、CSS、JS 不需要全部下载完成才开始工作

浏览器收到 HTML 字节后，按编码解码，进行词法与树构建，形成 DOM。解析到样式表、脚本和图片等引用，会安排子资源请求；预加载扫描器也可能提前发现资源。HTML 下载和解析通常能够交错进行。

CSS 被解析为样式规则，浏览器通过层叠、继承与选择器匹配计算元素的最终样式。关键 CSS 往往阻塞首次渲染，却通常不直接阻塞 HTML 解析；但依赖样式的脚本可能等待样式表，进而间接阻塞解析。过程概览见 [MDN：浏览器如何工作](https://developer.mozilla.org/en-US/docs/Web/Performance/Guides/How_browsers_work)。

| 脚本方式 | 加载与执行 | 对页面解析的影响 |
| --- | --- | --- |
| 普通解析器插入的经典脚本 | 遇到后加载并执行 | 通常阻塞后续 HTML 解析 |
| 外部经典脚本 `defer` | 并行下载，解析完成后按文档顺序执行 | 避免因下载阻塞解析，执行完成后才推进 DCL |
| 外部脚本 `async` | 并行下载，就绪后尽快执行 | 执行仍占主线程，不保证文档顺序 |
| `type="module"` | 默认具有延后执行行为，并加载依赖图 | 不能把经典脚本规则原样套用到所有模块情形 |

`async` 的意思不是“JS 在另一个线程并行操作 DOM”。动态插入脚本还有不同规则，具体以 [MDN script 元素](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/script) 为准。

### 样式、布局、绘制、光栅化和合成各回答一个问题

用一张营业额卡片做例子：显示“12,500 元”，白底、宽 300 像素，放在页面左侧。

| 阶段 | 回答的问题 | 卡片示例 |
| --- | --- | --- |
| 样式计算 Style | 它应该是什么样式？ | 字号、颜色、宽度、display |
| 布局 Layout | 它在哪里，多大，文字如何换行？ | 计算位置、尺寸和行盒 |
| 绘制 Paint | 按什么顺序画哪些内容？ | 背景、边框、文字的绘制记录 |
| 光栅化 Raster | 如何把绘制记录转成像素内容？ | 为图块生成可用的像素资源 |
| 合成 Composite | 如何组合已有内容形成一帧？ | 按变换、裁剪和层次组合结果 |
| 提交与显示 | 何时真正出现在屏幕？ | 帧交给显示系统并参与屏幕刷新 |

常见教材用“DOM + CSSOM → 渲染树”概括可渲染结构。它适合建立入门关系，但真实引擎还有布局树、片段、绘制记录、属性树和合成结构等，不是永久维护一棵万能树。

`display: none` 的元素通常不生成布局盒，`visibility: hidden` 通常保留布局占位但不显示内容，`opacity: 0` 的元素通常仍参与布局，甚至可能接受命中测试。透明、不可见和不存在于布局中是不同状态。

Paint 更接近生成绘制操作，而非所有像素都已显示；Raster 将这些操作转换成像素，之后还有合成和提交。Blink/Chromium 的教学流程可参考 [Chrome 渲染器内部工作原理](https://developer.chrome.com/blog/inside-browser-part3)。

### 重排、重绘与合成：改了哪个输入，就重做哪些工作

这里常说的术语是**重排、重绘、合成**；“重合”通常是对“重绘”或“合成”的混称。

重排也叫回流，通常对应重新布局：几何信息失效，需要计算位置和尺寸。重绘是外观变化后重建受影响的绘制内容。合成则把已有内容组合成最终帧，有些变化可以复用已光栅化的内容而不再布局和绘制。

| 修改 | 常见受影响阶段 | 原因 |
| --- | --- | --- |
| 改宽度、字号、追加会换行的文字 | 样式 / 布局 / 绘制 / 后续阶段 | 几何关系或内容变化 |
| 改背景色 | 样式 / 绘制 / 后续阶段 | 外观变了，几何可能不变 |
| 合适条件下的 transform / opacity 动画 | 可能主要是合成 | 复用已有内容改变变换或透明度 |

这是常见路径，不是“某 CSS 属性永远只触发某阶段”的保证。层分配、图块可用性、绘制影响和实现条件都可能改变路径。`transform` 并不保证免费，`will-change` 只是提示，滥用会增加内存和管理成本。优化应依据实际录制结果，参考 [web.dev 渲染性能](https://web.dev/articles/rendering-performance)。

新增一行模型回答可能让气泡增高、后续消息下移，这是合理的布局工作；问题在于是否为每个字符反复做相同工作，甚至重新解析整个历史消息列表。

### 强制同步布局：为什么“写一下再读一下”会变贵

浏览器通常可以推迟并合并布局，但 JS 修改几何样式后立即读取需要最新布局的属性，可能迫使浏览器提前完成布局。若每个循环都这样做，就容易形成布局抖动。

```js
// 教学反例：每轮写样式后立刻要求最新几何信息。
for (const card of cards) {
  card.style.width = "320px";
  console.log(card.offsetWidth);
}

// 先批量写，再集中读，通常可以减少反复强制布局。
for (const card of cards) card.style.width = "320px";
const widths = Array.from(cards, card => card.offsetWidth);
```

第二种方式仍可能触发布局，改进点是避免每个元素反复交替“写—算—读”。如果目标是读取修改前的尺寸，应先统一读取旧值，再批量写入。相关机制见 [web.dev：避免强制同步布局与布局抖动](https://web.dev/articles/avoid-large-complex-layouts-and-layout-thrashing)。

### 事件循环：数据到了，页面为什么还没更新

网络接收、定时器计时和 JS 执行并不全在同一条线程上，但页面 DOM 操作与大量渲染工作需要主线程参与。主线程长时间执行脚本时，即使网络已经收到回答，也可能无法及时处理回调并显示。

理解事件循环时，可以抓住任务、微任务检查点和渲染机会：事件处理等任务执行后，在规定的检查点清空微任务；浏览器在合适的渲染机会更新画面。Promise 回调常作为微任务，连续不断地产生微任务可能饿死后续任务和渲染。调度规则可查 [HTML 标准的事件循环章节](https://html.spec.whatwg.org/multipage/webappapis.html#event-loops)。

`requestAnimationFrame` 把回调安排到一次渲染更新中、通常在绘制前运行，但不是“回调结束已经上屏”，也不能保证每个事件循环都绘制一次。后台标签页通常会节流或暂停相关更新。屏幕 60 Hz 时一帧约 16.7 ms，120 Hz 时约 8.3 ms，这些时间还要留给样式、布局、绘制与系统工作。

Web Worker 适合把独立计算移出主线程，但不能直接操作 DOM；Worker 与页面常通过 `postMessage` 通信，结构化克隆或可转移对象会影响传输成本。一个 Worker 不必对应一个独立操作系统进程，Web API 层的通信也不能直接等同于某次底层 IPC。

`DOMContentLoaded` 主要标记文档解析及相关延后脚本阶段完成，不必等所有图片；`load` 还等待通常应阻塞它的依赖资源，但不代表之后没有请求。FCP、LCP 描述可见内容出现，INP 关注交互响应，CLS 关注视觉稳定性。不能用一个 `load` 时刻代替全部用户体验。

## 6. 模型请求：在后端接上检索、工具与推理

### 点击“分析原因”后，又发生一次普通 Web 请求

点击事件进入页面主线程，应用读取输入，展示等待状态，通过 `POST /api/chat` 发送消息。它仍要经过浏览器网络服务、连接、网关和业务服务，只是可能复用已建立的连接。首屏曾经成功，并不保证这次请求的会话、权限与网络仍然有效。

浏览器通常请求自有后端，由后端管理模型服务凭据、权限、额度和审计。如果直接调用第三方，也应设计短期受限凭据等机制，不能把长期服务端密钥打包进前端 JS。

应用先创建或识别 `requestId`、会话与本轮生成记录，再校验用户是否能查看目标门店。开始发送流式响应后，HTTP 状态码已经提交，后续错误需要通过约定的事件报告；前端不能把“收到 200”直接显示为“回答成功”。

### RAG 和工具调用分别补充哪种能力

“营业额为什么下降”需要事实。RAG 可以检索经营规则、活动说明和门店文档；营业额、客流、客单价等实时数据更适合通过受控查询工具获取。向量相似度不能代替数据库里的准确数字，工具参数也不能代替授权。

一条可解释的应用编排可以是：

1. 根据登录态确定租户、门店范围和可见文档。
2. 查询昨天与对照周期的营业额、订单量、客单价。
3. 按权限过滤后检索相关活动、闭店或商品缺货记录，必要时重排。
4. 将问题、数据、来源和必要历史放入提示词，并限制上下文长度。
5. 让模型生成有依据的解释，对无法证实的原因保留不确定性。

模型若提出工具调用，运行时负责校验工具名、参数和权限，执行后把结果作为新的输入交给模型。这会形成“模型 → 工具 → 模型”的多轮循环，而不是一次连续 Decode 就自动访问数据库。

检索内容属于外部数据，不能因为其中写着指令就覆盖系统权限；工具结果也应保留来源与时间。检索缓存要考虑租户、权限和文档版本，答案缓存还需考虑问题、上下文、数据新鲜度与模型配置。

### 推理服务内部：排队、Prefill、Decode

后端请求模型 API 后，推理服务通常先进行准入、排队和分词，把文本转换为 token ID，再由调度器安排计算。Token 是模型词表中的单位，不能固定换算为一个汉字或一个英文词。

**Prefill 处理输入上下文，Decode 逐步生成后续 token。**对于常见自回归 Transformer，Prefill 计算输入序列的表示并建立 KV 状态，随后根据当前上下文得到下一个 token 的分布、采样或选择，再把新 token 纳入后续上下文。

Prefill 能在已知输入上利用较多并行计算；常规 Decode 则依赖之前生成的结果。投机解码等优化可以改变一次推进的方式，因此“一次调度永远恰好生成一个 token”也不是通用事实。

长输入通常增加 Prefill 工作和 KV 占用，长输出增加持续生成时间。首 token 慢可能是排队或输入处理慢；首 token 很快但整体很久，可能是输出较长或 Decode 吞吐不足。

### KV Cache 缓存的是注意力中间状态

Transformer 在生成新 token 时需要访问历史上下文的注意力信息。KV Cache 保存各层历史 token 的 Key、Value，避免每一步都重新计算历史部分。它不是最终答案缓存，也不能消除新 token 的全部计算。

普通密集 KV 存储的近似载荷可以写成：

```text
KV 字节数 ≈ 2 × 层数 × KV 头数 × 每头维度
              × 已缓存 token 数 × 每元素字节数
```

教学假设为 32 层、8 个 KV 头、每头 128 维、4,096 token、BF16 每元素 2 字节，得到约 512 MiB。这里只算一个序列的 KV 载荷，不含模型权重、激活、分配开销等；GQA/MQA、量化、滑动窗口、并行切分和共享前缀都会改变实际显存需求。

PagedAttention 以块管理 KV 存储，减少某些连续分配带来的浪费；它不会让 KV 不占显存。前缀缓存可在满足精确匹配等条件时复用已有前缀计算，同样不是复用完整答案。相关实现思路见 [Hugging Face PagedAttention 说明](https://huggingface.co/docs/text-generation-inference/en/conceptual/paged_attention)。

Continuous batching 让服务在生成推进过程中动态纳入新请求、移出已完成请求，提高资源利用率。吞吐、排队时间和单用户 token 间隔之间需要权衡；并发开得越大，不代表每个用户更快。Chunked prefill 还可以分块处理输入，在特定调度策略下与 Decode 工作交错；配置边界见 [vLLM 优化文档](https://docs.vllm.ai/en/stable/configuration/optimization/)。

## 7. 流式输出：从模型 token 到浏览器的一次绘制

### 流式输出不是不断发送新的完整 HTTP 请求

服务端可以保持一次响应打开，在生成过程中逐步发送数据。SSE 是一种基于 HTTP 的文本事件格式，常用 `Content-Type: text/event-stream`；WebSocket 则提供双向消息通道。模型流式输出不强制使用 WebSocket，选择取决于交互协议。

原生 `EventSource` 适合 GET 订阅，有自动重连能力，但不能像 Fetch 一样任意设置 POST 请求体与请求头。

聊天发送 JSON 请求体时，常用 `fetch()` 发 POST，再读取响应的 `ReadableStream`。采用 SSE 格式并不意味着必须使用 `EventSource`。参见 [MDN SSE 使用指南](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)。

下面是本文自定义的事件协议示例，不是所有模型供应商通用格式。每个事件以空行结束：

```text
event: delta
id: answer-7:1
data: {"text":"昨天的营业额"}

event: delta
id: answer-7:2
data: {"text":"下降，主要来自订单量减少。"}

event: done
id: answer-7:3
data: {"finishReason":"stop"}

```

`done`、错误格式与恢复协议都需要应用约定。流结束可能是正常完成，也可能是代理超时或连接断开；不能把 EOF 一律当作成功。流式提供更早的可见反馈，并不自动减少总计算量，参考 [Hugging Face 流式生成说明](https://huggingface.co/docs/text-generation-inference/en/conceptual/streaming)。

### 六种边界不能画成一个等号

**模型 token、文本增量事件、服务端 write、HTTP 数据帧、浏览器 read 返回的 chunk、一次 UI 更新，彼此都不保证一一对应。**一个 token 可以属于某个词的一部分，一次事件可能包含多个 token，一次读取也可能只有半条事件。

网络与代理可以拆分或合并数据。甚至一个 UTF-8 汉字的字节也可能被分到两次读取中，所以浏览器不能对每个 chunk 独立用普通解码后就直接 `JSON.parse`。

正确接收流程应当分层：

1. 使用 `TextDecoderStream` 或 `TextDecoder.decode(bytes, { stream: true })` 连续解码，保留未完成字符状态。
2. 把文本追加到解析缓冲区，按协议识别行、空行与完整事件，保留半条事件。
3. 对 SSE 正确处理 LF/CRLF、多行 `data:`、注释与事件字段；生产中使用符合 [HTML SSE 解析规则](https://html.spec.whatwg.org/multipage/server-sent-events.html#parsing-an-event-stream) 的成熟解析器。
4. 对完整事件的 data 做 JSON 解析，再按事件类型更新业务状态。
5. 收到约定的完成事件才标记成功；取消、失败和正常完成分别处理。

HTTP/1.1 可使用 chunked 传输编码，HTTP/2 和 HTTP/3 有各自的数据帧机制；它们都不是应用 SSE 事件边界。不要把 `Transfer-Encoding: chunked` 当成所有 HTTP 版本流式响应的必需头。

### 后端在流式发送，前端为何最后一口气出现

最常见的排查方向是缓冲：应用框架没有及时 flush，压缩器在攒数据，反向代理启用了响应缓冲，客户端调用了 `response.text()` 等待整个正文，或者前端虽然收到增量却迟迟没有绘制。

应逐段记录“模型首增量、应用首写、代理后首字节、浏览器首事件、首个可见字符”。针对流式路由配置适当的响应缓冲、空闲超时和缓存策略，并验证代理产品的实际行为。服务端 flush 只是提交给下一层，不保证该字节立刻上屏。

心跳可以防止某些空闲超时并帮助探测连接，但不能保证任务仍在正常推进。SSE 的 `id` 与 `Last-Event-ID` 只提供恢复线索；没有服务端保存、重放和去重能力，自动重连不会自动恢复丢失内容，更不会自动续跑模型任务。

### 将网络频率和 UI 更新频率分开

流里每次来一点内容都重新解析整篇 Markdown、更新全部聊天记录，会放大主线程开销。可以先累积增量，再按帧或短时间窗口更新当前回答；历史消息保持稳定，代码高亮等重活可以延迟或分段执行。

下面只演示“增量累积后按帧写入文本节点”，不包含 SSE 解析、状态管理和错误恢复。`target` 是调用方传入的回答容器：

```js
function createTextWriter(target) {
  const textNode = document.createTextNode("");
  target.replaceChildren(textNode);
  let pending = "";
  let frame = null;

  function flush() {
    frame = null;
    if (pending) textNode.appendData(pending);
    pending = "";
  }

  return {
    append(delta) {
      pending += delta;
      if (frame === null) frame = requestAnimationFrame(flush);
    },
    finish() {
      if (frame !== null) cancelAnimationFrame(frame);
      flush();
    },
  };
}
```

追加文本仍可能触发布局和绘制；这个例子降低的是更新次数，并不消除渲染成本。终止、卸载、后台页面节流和超大输出还需在实际应用中处理。Markdown 应经过可信的解析与清洗，不能把模型输出直接交给 `innerHTML`。

用户点击停止后，前端可用 `AbortController` 中止本地请求，但后端和模型调度器还需要接收取消并释放资源。“停止显示”不代表“停止生成或计费”。慢客户端还需要背压或有界缓冲策略，不能无限在内存里积累输出。

## 8. 用同一条时间线排障，再把主线复述出来

### 页面慢与模型慢，先统一测量起点

页面侧可以结合 Network 瀑布图、Performance 录制和 Navigation Timing。以下代码适合在浏览器控制台观察当前文档导航，单位为毫秒；它不测量后续 SPA 路由和模型请求：

```js
const nav = performance.getEntriesByType("navigation")[0];
if (nav) {
  console.table({
    dns: nav.domainLookupEnd - nav.domainLookupStart,
    connectIncludingTls: nav.connectEnd - nav.connectStart,
    tls: nav.secureConnectionStart > 0
      ? nav.connectEnd - nav.secureConnectionStart : 0,
    requestToFirstByte: nav.responseStart - nav.requestStart,
    download: nav.responseEnd - nav.responseStart,
    domContentLoaded: nav.domContentLoadedEventEnd - nav.startTime,
    load: nav.loadEventEnd > 0 ? nav.loadEventEnd - nav.startTime : null,
  });
}
```

TLS 是连接阶段的一部分，不能再与 `connectIncludingTls` 相加。连接复用、缓存、协议和计时限制可能让某些阶段为零；`requestToFirstByte` 也不能直接叫“后端执行时间”，其中包含网络与排队。

字段定义见 [MDN PerformanceNavigationTiming](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming)。

对模型，至少拆出三个指标：请求到首个生成 token 的 TTFT、生成 token 之间的间隔、请求到完整回答结束的时长。还应单独测“用户点击到首个可见字符”，因为接收 token 后，可能还有事件解析、批量更新和渲染等待。

一个教学近似式是：

```text
首个可见回答耗时
≈ 请求到达应用的耗时
 + 鉴权 / 数据查询 / 检索 / 编排关键路径
 + 模型排队与 Prefill / 首 token 生成
 + 下行网络与中间层缓冲
 + 浏览器解析、调度和首次可见渲染
```

这些阶段可能重叠，公式用于定位构成，精确分析应依据时间戳和 Trace 的关键路径。多机时间需要校准；不要直接拿浏览器的相对时间减服务器墙上时钟。

### 从现象找到该看的证据

| 现象 | 先看什么 | 不要过早下的结论 |
| --- | --- | --- |
| 域名偶尔打不开 | DNS 结果、解析错误、IPv4/IPv6 与代理路径 | 一定是后端挂了 |
| 建连或 SSL 阶段很长 | 连接是否复用、丢包、握手和证书错误 | 一定是 SQL 慢 |
| Waiting / TTFB 很长 | 网关与应用 Trace、排队、池等待、下游耗时 | TTFB 全是数据库耗时 |
| 文件返回很快，页面仍白屏 | 关键 CSS、脚本错误、长任务、渲染记录 | 网络快所以前端正常 |
| 页面出现但点击迟钝 | 输入延迟、事件处理、布局与下一帧 | 只需要加带宽 |
| 模型首字很慢 | 检索、工具、排队、Prefill 分段计时 | 一定是显卡 Decode 慢 |
| 首字快，后续卡顿 | token 间隔、代理缓冲、客户端长任务 | 一定是模型断流 |
| 回答最后一次性出现 | 应用/代理 flush、客户端流读取、UI 批处理 | 服务端没有生成增量 |
| 点停止仍占用资源 | 取消是否传到运行时和推理服务 | Abort 等于全链路停止 |

排查时沿一个 `requestId` 关联浏览器事件、入口日志、应用 Trace 和模型请求标识。记录阶段与错误原因即可，不应为了关联请求而默认把完整提示词、Cookie 和业务隐私数据写入日志。

### 先学这几个节点，再扩展整张知识网

第一轮先掌握 URL、HTTP 缓存、DNS、TCP/TLS、请求响应、后端一次查询、DOM/CSS、布局绘制合成。第二轮补连接复用、跨域、进程通信、事件循环、线程池和数据库故障。第三轮再接 RAG、推理调度、KV Cache、流式恢复与性能治理。

每轮都用同一个场景手跑：打开后台，观察一次资源缓存命中；查看一个 API 的时序；修改元素宽度并录制布局；再对比模型的首事件与首字符时间。能把每个现象落到具体阶段，比仅仅记住定义更有用。

### 30 秒复述：先把骨架讲完整

> 输入 URL 后，浏览器处理导航，依据缓存和连接状态决定是否解析 DNS、建立 TCP/TLS 或 QUIC 连接。请求经接入层到后端，完成鉴权和数据处理。HTML 返回后，浏览器边解析边加载资源，执行脚本，经过样式、布局、绘制、光栅化和合成显示页面。AI 请求复用这条网络链，在后端增加检索、工具和模型推理，把增量通过流式响应送回前端，再持续更新页面。

### 两分钟复述：把分支和责任边界补齐

> 我会先区分页面导航、业务 API 和模型请求。输入网址时，URL 的片段不会随普通 HTTP 请求发送；新鲜 HTTP 缓存可以直接复用，需要验证时才可能得到 304。需要网络时，解析器帮助得到地址，浏览器优先复用连接；HTTP/1.1、HTTP/2 通常走 TCP 与 TLS，HTTP/3 走 QUIC。
>
> 请求到接入层后可能命中 CDN，也可能由代理转发给后端。应用先验证用户与资源权限，再查缓存、数据库或下游。线程池、连接池、锁和排队都会影响响应，不能把全部 TTFB 都算成数据库时间。
>
> 返回 HTML 后，网络服务把数据交给渲染器，浏览器边解析边加载资源，JS 和 DOM 更新主要在主线程推进。样式决定外观，布局计算几何，绘制记录操作，光栅化生成像素，合成组织最终帧。改尺寸通常需要布局，改颜色可能只需重绘，满足条件的变换可以主要走合成；主线程长任务会推迟可见更新。
>
> 模型请求再增加会话、权限、检索或工具、排队、Prefill 和 Decode。KV Cache 保存注意力中间状态，流式协议把生成增量送回浏览器。网络 chunk 不等于 token 或完整事件，前端要连续解码、按协议分帧、批量渲染，并区分完成、错误和取消。排障时分别看首字节、首 token 与首个可见字符。

下一次遇到一个新概念，可以把它放回三个问题里：它位于哪一段，输入输出是什么，失败时能看到什么证据。从一个网址开始，这条主线就能持续连接浏览器、网络、后端与模型应用。
