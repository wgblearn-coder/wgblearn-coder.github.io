Redis 难的地方不是命令多，而是同一条命令放进不同业务流程后，保证范围会变。比如菜单缓存命中很快，遍历一个大集合却可能拖慢整个实例；`INCR` 虽然原子，订单仍可能重复；数据库已经提交，缓存也仍可能返回旧值；主从复制和 AOF 都配上了，故障切换后仍可能丢失已成功返回的写入。

下面沿着一条业务链来讲：用户打开餐厅菜单、查询菜品、提交订单、扣减库存，系统更新缓存，再异步处理经营事件。每一部分都回到这条链上，看看机制解决了什么，又留下了什么边界。

> 阅读范围：以 Redis Open Source 常见单实例、Sentinel 和 Cluster 架构为主。命令示例采用 Redis 7.x 常用能力；涉及版本差异会单独说明。官方资料核对日期为 2026-09-07。文中的容量、流量、TTL 和超时均为教学示例，不代表生产实测或通用配置。托管产品的代理、持久化和故障切换语义应按其产品文档另行确认。

## 从业务位置到请求执行：Redis 为什么快

### 先看哪几段

| 主线 | 要理解的原理 | 能解决的实际问题 |
| --- | --- | --- |
| 请求如何执行 | 内存访问、事件循环、I/O 多路复用、串行命令执行 | 为什么快，为什么会被慢命令拖住 |
| 数据如何组织 | 哈希表、SDS、listpack、quicklist、跳表 | 类型选择、BigKey、空间和性能突变 |
| 数据何时消失 | 惰性过期、主动过期、LRU/LFU 淘汰 | TTL、内存增长、缓存雪崩 |
| 多请求如何协作 | 原子命令、事务、WATCH、Lua | 限流、并发扣减、锁与幂等 |
| 多份数据如何一致 | Cache Aside、竞态、失效事件、版本控制 | 数据库和缓存不一致 |
| 故障后如何恢复 | RDB、AOF、复制偏移、故障选主、槽迁移 | 数据丢失、恢复时间、扩容 |
| 生产中如何判断 | 排队、带宽、内存、复制、回源指标 | 超时、抖动、热点、故障放大 |

第一次阅读可以先看执行模型、数据结构和缓存一致性，再进入持久化与集群。前面三部分会反复用到同一条请求链。

### Redis 到底是什么，应该放在系统的哪个位置

Redis 是一个以内存为主要工作数据存储介质、通过网络提供数据结构操作的服务。应用不是只能存取一个 JSON 字符串，还可以让 Redis 在服务端完成计数、集合判断、有序排名等操作。

以餐饮系统为例，常见职责划分如下。

| 数据或操作 | Redis 的用途 | 最终保证放在哪里 |
| --- | --- | --- |
| 菜单、菜品详情 | 缓存，降低数据库读取压力 | 数据库保存事实数据 |
| 热门菜品排行 | ZSet 维护可快速查询的排名 | 是否可重建由事件源和业务设计决定 |
| API 限流 | 多应用实例共享原子计数状态 | 超限策略和故障策略由应用定义 |
| 订单提交去重 | 快速挡住短时间重复请求 | 数据库唯一约束及订单状态机 |
| 库存预扣 | 高并发入口的快速准入 | 库存账本、订单事务、对账补偿 |
| 消费处理进度 | Streams 消费组追踪待确认消息 | 业务幂等、持久化和恢复流程 |

Redis 也可以承担主存储角色，但这时要求完全不同。缓存丢了可以重建；主存储必须明确允许丢多少数据、多久恢复，以及怎样备份和审计。

```text
用户 → 应用：认证、租户与限流 → Redis 菜单缓存 → 命中后返回
                              ↓ 未命中且获得回源预算
                           数据库读取 → 回填缓存

提交订单 → 数据库事务：订单、库存与 Outbox
         → 提交后的失效消费者 → 删除相关缓存，失败可重试
```

Redis 支持哪些数据类型，与具体版本和发行形态有关。本文集中讨论通用核心类型，不把新版本的可选能力当成所有环境都具备的基础能力。[Redis 数据类型](https://redis.io/docs/latest/develop/data-types/)


### 一次请求实际经过哪些环节

应用执行 `GET dish:1001`，大致会经历：

```text
应用排队或等待可用连接
→ 编码 Redis 协议并发送
→ 网络传输
→ 服务端读取请求、解析命令
→ 等待命令执行机会
→ 查找 key，检查是否过期，读取 value
→ 编码并发送响应
→ 客户端解析、反序列化
→ 应用得到对象
```

因此：

```text
端到端耗时 ≈ 客户端等待 + 网络往返 + 服务端排队
           + 命令执行 + 响应传输与反序列化
```

“Redis 命令执行只用了几十微秒”不代表业务接口也只用几十微秒。连接等待、跨区域网络、大响应、应用 GC 都可能成为主要部分。

### 内存访问降低了什么成本

常见读写操作直接访问内存中的数据结构，避免每次读取都同步等待磁盘随机 I/O。与此同时，Redis 通过专门的数据结构减少需要检查的元素数量。

例如读取菜品名称，理想路径是通过哈希定位 key，再读取短 value；不需要扫描全部菜品，也不需要解析整个数据库页面层次。

但“在内存里”并不意味着成本为零：哈希计算、内存分配、缓存未命中、对象复制、协议编码和网络传输都需要时间。一个 20 MB 的 JSON 即使已经在内存里，读取它仍需要传输 20 MB 并在应用中解析。

### 单线程与 I/O 多路复用分别负责什么

在常见执行模型里，核心键空间命令主要由主执行线程串行处理。网络 I/O、后台释放和持久化可能使用其他线程或子进程，具体取决于版本和配置。

I/O 多路复用允许一个事件循环监听许多连接。哪个连接可以读写，操作系统就通知 Redis 处理；Redis 不需要给每个连接配置一个阻塞等待的业务线程。

两个概念的区别是：

- **I/O 多路复用**解决同时管理大量连接的问题。
- **命令串行执行**简化共享数据结构上的并发控制，使短命令可以连续快速执行。

假设主线程平均每条命令占用 10 微秒，那么纯粹按执行时间估算，理论量级是每秒 10 万条。这只是忽略网络、调度和其他成本的算术上限，不能当作实例容量承诺。

一条命令占用主线程 100 毫秒，其间其他需要主线程执行的请求就会排队。实例平均 CPU 未满，也可能出现严重长尾延迟：观察整机 16 核 CPU 平均值，会掩盖单个执行核已经繁忙的问题。

先限制单条命令的工作量和响应体，再考虑连接数与机器规格。增加客户端线程并不能消掉同一个串行执行瓶颈。[Redis 延迟诊断](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/latency/)

### Pipeline 为什么提高吞吐，却不提供原子性

连续执行 100 次独立查询，若每次网络往返为 1 毫秒，仅串行往返就约需 100 毫秒。Pipeline 允许客户端连续发送多条命令，然后批量读取响应，减少逐条等待往返的开销。

它不改变命令本身的计算复杂度，也不保证这一批命令之间没有其他客户端命令穿插。

```text
Pipeline：减少通信等待
MULTI/EXEC：一组命令执行期间不被其他客户端命令插入
Lua：把读取、判断、修改放到服务端一次连续执行
```

批量越大，客户端和服务端需要缓存的请求、响应就越多。按“命令数量、总字节数、最大等待时间”限制批次，用实际 P99 验证。批量超时后可能只有部分命令完成，不应直接重试整个包含 `INCR` 的批次。

Cluster 中批次还可能被客户端拆发到多个节点；这不产生跨节点事务。[Redis Pipeline 原理](https://redis.io/docs/latest/develop/using-commands/pipelining/)

## 数据如何组织和回收：结构、编码与内存


### 逻辑类型和底层编码是两回事

逻辑类型是应用看到的 String、Hash、List、Set、ZSet；底层编码是 Redis 实际如何组织内存。

同样是 Hash，小对象可以使用紧凑的连续内存编码，大对象可能转为哈希表。转换通常由元素数量、元素长度和配置阈值触发。

紧凑编码用较少指针、较连续的内存换取更好的空间效率和 CPU 缓存局部性，代价是一些查找或修改需要顺序扫描、移动内容。元素少时，短距离扫描可能比多次指针跳转更便宜。

因此，“Hash 查询是 O(1)”描述的是典型哈希表模型；理解内部编码时，还要知道小集合可能采用受阈值约束的线性扫描。不要为了省内存把紧凑编码阈值无限调大。[内存优化与编码转换](https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization/)

可以在隔离测试实例中观察：

```redis
HSET demo:dish:1001 name noodles price_cent 2800
TYPE demo:dish:1001
OBJECT ENCODING demo:dish:1001
MEMORY USAGE demo:dish:1001
```

`TYPE` 返回逻辑类型，`OBJECT ENCODING` 返回当前编码；具体结果不能脱离 Redis 版本和配置背诵。[OBJECT ENCODING](https://redis.io/docs/latest/commands/object-encoding/)

### String：不仅是文本，也是计数和二进制容器

Redis String 可以保存字节序列。典型实现使用 SDS 等内部表示，并对可表示的整数、小字符串做编码优化。

SDS 的关键思想是记录长度和可用空间，使长度查询不必逐字节寻找结束符，也能保存包含零字节的二进制内容。预留容量减少某些追加操作的重复分配；但扩容、复制和大块分配仍有成本。

SDS 头部、长度读取等实现可参考 [Redis 7.2 的 sds.h](https://github.com/redis/redis/blob/7.2/src/sds.h)。这里说明的是典型实现，升级版本时不应依赖内部对象布局。

适合场景：菜品 JSON 缓存、整数计数、短状态值。

```redis
SET demo:dish:1001 '{"name":"noodles","priceCent":2800}' EX 300
GET demo:dish:1001
INCR demo:pageviews:1001
```

若多个客户端执行 `GET → 本地加一 → SET`，会发生丢更新。`INCR` 把读取与修改合成单条原子命令，避免这类竞争。

但 `INCR` 超时后结果可能已经生效。再次 `INCR` 是另一次增加，不是自动重试同一次操作。

### Hash：适合字段级访问，不等于把整个数据库塞进一个 key

Hash 保存 field-value，适合菜品基本字段、短会话状态等对象。

```redis
HSET demo:dish:1002 name rice price_cent 1800 stock 100
HMGET demo:dish:1002 name price_cent
HINCRBY demo:dish:1002 stock -1
```

字段级读取和更新避免反复传输整个 JSON。不过 `HINCRBY stock -1` 本身不会检查是否还有库存，也不会与数据库订单自动形成同一事务。

一个门店一个巨大 Hash，可能减少 key 数量，却也让所有字段集中在一个 Redis key 和一个分片上，形成 BigKey 或热点。对象边界应同时考虑读取粒度、生命周期、容量和分片单位。

不要再笼统地说“Hash 字段不能过期”：Redis 7.4 起提供 `HEXPIRE` 等字段过期命令；旧版本和部分兼容实现未必支持。采用前检查服务端与客户端能力。[HEXPIRE 版本与语义](https://redis.io/docs/latest/commands/hexpire/)

### List：两端操作高效，中间随机访问不是优势

常见实现通过 quicklist 将多个紧凑节点串联，节点内部可使用 listpack。这样兼顾两端插入和较低指针开销；不同版本可能使用不同编码组合。

```redis
LPUSH demo:jobs job-1001
RPOP demo:jobs
```

适合有界队列、栈、最近访问记录。两端单元素操作通常很便宜；定位中间元素、返回大量元素则需要更多遍历或复制。

直接 `RPOP` 的问题是消息取出后已经离开队列，消费者此时崩溃会丢任务。可靠处理需要待处理区、确认和超时接管，例如自行组织 `LMOVE/BLMOVE` 模式，或者使用 Streams 消费组。

### Set：成员判断高效，不意味着全量集合运算便宜

Set 保存不重复成员，常见编码包括 intset、listpack 或哈希表，取决于元素与版本。

```redis
SADD demo:favorite:user:10 dish-1001 dish-1002
SISMEMBER demo:favorite:user:10 dish-1001
```

它适合收藏去重、标签成员判断。集合交并差的成本与参与集合规模相关，`SMEMBERS` 还会返回整个集合。

“用 Redis 做交集很快”必须补充输入有多大、请求频率多高、结果有多少。大规模动态交集不应直接放进每个在线请求里。

### ZSet：为什么既能查成员，又能按分数范围查询

ZSet 中成员唯一，每个成员关联 score。常见的大集合编码同时维护：

- 哈希字典，便于按 member 查找分数。
- 跳表，便于按 score 和 member 顺序定位、遍历。

跳表在有序链表之上增加多层索引。查询先在稀疏的高层快速跳过大量元素，再向低层逐步精确定位，平均查找和插入复杂度为 O(log N)。范围查询定位起点后向后遍历 M 个结果，典型复杂度为 O(log N + M)。

```redis
ZADD demo:rank:store:20 120 dish-1001 90 dish-1002
ZINCRBY demo:rank:store:20 1 dish-1002
ZRANGE demo:rank:store:20 0 9 REV WITHSCORES
```

适合排行榜、按时间排序的数据、滑动窗口限流索引。

注意三个边界：同分成员按成员字节序排序；score 是双精度浮点数，不能随意塞入超大整数组合；一个全站排行榜仍然是一个 key，Cluster 不会把它自动拆到多个分片。

上述各类型的命令成本还受返回结果数量影响，不能只背容器查找复杂度。[类型选型](https://redis.io/docs/latest/develop/data-types/compare-data-types/)

### Bitmap、HyperLogLog 与 Bloom Filter：用空间换什么

| 结构 | 原理 | 适用问题 | 关键边界 |
| --- | --- | --- | --- |
| Bitmap | 以 bit 表示布尔状态，底层建立在 String 上 | 连续用户编号的签到、活跃标记 | 稀疏超大 ID 会撑大空间，应先做编号映射或分桶 |
| HyperLogLog | 从哈希值的统计特征估算基数 | UV、去重数量估算 | 只能近似计数，不能列出成员或做精确成员判断 |
| Bloom Filter | 多个哈希位置共同表示成员可能存在 | 拦截大量不存在的查询 | 可能误报；标准结构不直接支持删除，组件能力需检查 |

Bloom Filter 在正确插入且结构未损坏的前提下，对已加入元素不会给出不存在判断。但实际系统若新增数据未及时加入过滤器，仍可能错误拒绝合法请求。这是同步链路问题，不能用理论性质掩盖。

对于 n 个元素、目标误报率 p，经典 Bloom Filter 的理想参数约为：

```text
bit 数 m ≈ -n × ln(p) / (ln 2)²
哈希函数数 k ≈ (m / n) × ln 2
```

例如 n = 100 万、p = 1%，位数组约需 958 万 bit，即约 1.14 MiB，尚未计入实现元数据和扩容层。容量超出设计值时，误报率通常上升。

### 哈希表与渐进式 rehash：为什么扩容也影响延迟

Redis 键空间需要通过 key 定位 value。以 Redis 7.2 的字典实现为例，哈希函数把 key 映射到桶，碰撞时继续在对应桶中查找。平均定位成本较低，但并不意味着任意数据、任意状态下都严格 O(1)。

元素数量增长后，桶过于拥挤会增加碰撞，需要扩容并重新分配元素所在的桶。如果把所有元素一次迁移完成，大字典会长时间占住主执行线程。

渐进式 rehash 将迁移拆成许多小步骤：迁移期间保留新旧两张表，查找可能需要检查两者，新插入进入新表，旧表的桶随后逐步迁移；完成后释放旧表结构。

```text
旧表：一部分桶已迁移，一部分桶待迁移
新表：已迁移元素 + 新插入元素
每次推进少量工作 → 最终用新表替换旧表
```

渐进式 rehash 把一次集中停顿摊开了，却没有消除成本：新桶数组分配、迁移 CPU 和两张表并存的额外内存仍要算进去。后台持久化期间，扩容还会受写时复制影响。“渐进式”也不是独立线程免费完成的。[Redis 7.2 字典实现](https://github.com/redis/redis/blob/7.2/src/dict.c)

批量预热和大规模导入时，应逐步增加写入，边看延迟和内存。只按导入完成后的稳定占用配置容量，容易漏掉过程峰值。


### TTL 是有效期，不是一个精确触发的业务定时器

Redis 通过两类机制处理过期数据：访问 key 时检查有效期；后台周期性进行主动过期工作。具体扫描预算与算法随版本和配置演进。

这意味着逻辑上已经过期的 key 不应再作为有效数据返回，但内存回收和相关通知不一定发生在截止时刻。

```redis
SET demo:code:10 123456 EX 60
TTL demo:code:10
```

`TTL` 返回 `-1` 表示 key 存在但无过期时间，`-2` 表示 key 不存在。普通 `SET` 覆盖已有值通常会清除原 TTL，除非显式设置新有效期或使用支持的 `KEEPTTL`。字段或数值原地修改与覆盖整个 key 的 TTL 行为不同，应检查具体命令。

设置值和 TTL 尽量使用单条 `SET ... EX/PX`。拆成 `SET` 和 `EXPIRE`，中间崩溃会留下无过期时间的数据。[EXPIRE 语义](https://redis.io/docs/latest/commands/expire/)

订单超时关闭不能只依赖过期通知。更可靠的方式是把截止时间和订单状态写进数据库，用延迟任务或扫描推动执行，并通过条件更新确保只关闭仍未支付的订单；Redis 可以加速调度。

### 淘汰是在内存压力下选择牺牲谁

过期由时间触发；淘汰由内存压力触发。两者相互独立，所以一个 TTL 还剩五分钟的缓存，也可能因为淘汰提前消失。

常见策略：

| 策略 | 选择范围与倾向 | 适用考虑 |
| --- | --- | --- |
| `allkeys-lru` | 全部 key，近似淘汰较久未访问的数据 | 访问具有近期局部性的纯缓存 |
| `allkeys-lfu` | 全部 key，近似淘汰较少访问的数据 | 热门数据较稳定的缓存 |
| `volatile-lru/lfu` | 仅设置了过期时间的 key | 需要明确区分可淘汰数据的混合场景 |
| `volatile-ttl` | 仅带 TTL 的 key，倾向剩余有效期较短者 | 有特定有效期语义的缓存 |
| `allkeys-random/volatile-random` | 在对应范围内随机选择 | 简单随机淘汰场景 |
| `noeviction` | 不主动淘汰以腾出空间 | 希望显式暴露容量不足，应用必须处理写失败 |

Redis 的 LRU 使用采样近似，不维护每次访问都精确更新的全量 LRU 链表。LFU 通过近似频率计数及衰减避免历史热门永远占据缓存。

`volatile-*` 如果没有可选的过期 key，无法按预期释放空间；`noeviction` 下部分需要增加内存的写入会失败，不能理解成实例会永远正常工作。[淘汰策略](https://redis.io/docs/latest/develop/reference/eviction/)

### 为什么 maxmemory 不能等于容器内存上限

Redis 进程占用不只有业务 value，还包括 key、对象元数据、分配器开销、客户端和复制缓冲，以及持久化时可能出现的额外内存。

需要区分 Redis 内存统计、进程 RSS 和容器整体用量；它们口径不同。某些复制/AOF 缓冲不参与淘汰判断，不能将 `maxmemory` 当作进程 RSS 的硬上限。

因此先用真实数据装载测量，再为复制、持久化、碎片和流量波动预留空间。16 GiB 容器直接配置 16 GiB `maxmemory`，很容易在写入或后台任务高峰时被 OOM Kill。

缓存、锁、幂等记录和消息队列如果共用一个可任意淘汰的实例，会互相影响。按可靠性等级和流量特征隔离，比依赖“某个 key 平时不会被淘汰”更可靠。

## 从原子操作到缓存一致性：读写链路如何协作


### 单条命令原子，不代表多步业务原子

两个请求都执行以下逻辑：

```text
GET stock → 得到 1
如果 stock > 0
    DECR stock
```

可能得到：

```text
A 读取 1
B 读取 1
A 扣成 0
B 扣成 -1
```

每个 `GET`、`DECR` 都是原子的，但“检查再扣减”不是一个原子操作。

解决办法是将条件和修改放入同一个服务端操作，例如 Lua；或者用 `WATCH` 检测并发修改后重试。若库存事实在数据库，则还要在数据库中保护最终库存不变量。

### MULTI/EXEC 保证连续执行，但没有数据库式回滚

`MULTI` 开始排队，`EXEC` 执行排队命令。执行阶段其他客户端命令不会插入其中。

但要区分：排队阶段命令本身无效可能导致事务无法执行；执行阶段某条命令因类型不匹配出错，其他命令仍可能已经生效或继续执行。Redis 不提供通用回滚。

`WATCH key` 是乐观并发控制：监视对象在 `EXEC` 前发生变化，事务就不执行，应用需要重新读取和计算。高冲突热点下反复重试可能放大负载。

事务与 WATCH 依赖连接上下文，客户端使用方式必须确保相关命令在同一连接上，异常后正确清理状态。[Redis 事务](https://redis.io/docs/latest/develop/using-commands/transactions/)

### Lua 把条件判断移到数据旁边

下面展示单 key 库存准入的最小逻辑。它只解释 Redis 内部原子扣减，不是完整下单方案。

```lua
-- KEYS[1]：库存 key
-- ARGV[1]：需要扣减的正整数
local amount = tonumber(ARGV[1])
if not amount or amount <= 0 or amount ~= math.floor(amount) then
    return redis.error_reply('invalid amount')
end

local raw = redis.call('GET', KEYS[1])
if not raw then
    return -1 -- 库存状态缺失，交给应用按约定处理
end

local stock = tonumber(raw)
if not stock or stock < 0 or stock ~= math.floor(stock) then
    return redis.error_reply('invalid stock')
end

if stock < amount then
    return 0
end
redis.call('DECRBY', KEYS[1], amount)
return 1
```

所有参数与状态校验尽量放在写入之前。脚本执行不被其他客户端命令穿插，但运行错误不会自动撤销之前完成的写入。Lua 数值精度也有边界，示例约定数量在安全整数范围内。

脚本必须短小、有界，不应遍历全库或处理无法预测的大集合。`EVALSHA` 使用脚本缓存，缓存缺失时需处理 `NOSCRIPT`；脚本缓存不是可靠的业务数据存储。[Lua 执行语义](https://redis.io/docs/latest/develop/programmability/eval-intro/)

Cluster 下，脚本涉及的多个 key 通常需要位于同一 hash slot，并通过 `KEYS` 显式传入。[Lua API 与集群限制](https://redis.io/docs/latest/develop/interact/programmability/lua-api/)


### Cache Aside 的完整读写路径

读流程：

```text
先认证并确定租户、数据访问权限
→ 查询缓存
→ 命中则返回
→ 未命中则申请回源并发预算
→ 查询数据库
→ 回填缓存并附带有效期
→ 返回结果
```

写流程通常采用：

```text
提交数据库事务
→ 删除相关缓存
→ 后续读取从数据库重新加载
```

删除比直接更新缓存更容易处理多个查询视图，也减少并发写请求把旧结果覆盖到新缓存的机会。但它不是强一致协议。

### 为什么不能先删除缓存，再提交数据库

```text
时间   写请求 W                   读请求 R
T1     删除缓存
T2                               缓存未命中
T3                               数据库仍是旧值 v1，读取 v1
T4                               将 v1 写回缓存
T5     数据库提交 v2
```

此后缓存仍是 v1，所以常见顺序是数据库提交后再失效缓存。

这里的“提交后”很关键：在事务方法返回前调用 `DEL`，数据库事务可能还没有真正提交。Spring 的数据库 `@Transactional` 也不会自动把 Redis 操作纳入同一个原子事务。

### 为什么提交后删除，仍可能读到旧值

另一种时序：

```text
时间   读请求 R                   写请求 W
T1     缓存未命中
T2     从数据库读到 v1
T3                               数据库提交 v2
T4                               删除缓存成功
T5     把之前读到的 v1 回填缓存
```

这叫旧值回填。还有另一类问题：数据库提交成功，但缓存删除因网络或进程崩溃没有完成。

因此需要分别处理：

- **失效操作没有可靠执行**：通过 Outbox、CDC 或可持久重试任务恢复失效。
- **读写并发造成旧值回填**：限制回填窗口，或采用协调读写的版本/栅栏协议。

异步重试删除能改善第一类问题；不能宣称天然杜绝第二类问题。

### TTL 和延迟双删分别能做什么

TTL 是减少陈旧数据长期驻留的兜底。它限定一份缓存从写入后的存活期，却不严格等于“从数据库更新时开始最多陈旧这么久”：旧查询可能在更新很久以后才回填，之后又获得完整 TTL。

延迟双删试图在提交后再等一段时间删除，清理可能晚到的旧回填。但固定延迟无法覆盖所有慢查询、长事务、暂停和网络波动。它是降低竞态发生概率的措施，不是强一致性证明。

### 什么时候需要版本控制

可以为事实数据维护单调版本号，将 `{version, payload}` 写入缓存，并原子拒绝较旧版本覆盖较新版本。

但仅在缓存 value 中放版本仍不够：如果缓存已被删除，慢读请求带着 v1 回来，当前 key 不存在，比较逻辑仍可能接受 v1。

更完整的协议需要维护已知最小合法版本或失效栅栏，回填时原子检查。这个标记也不能过早过期、被淘汰或在切换时回退；数据库事务和标记传播之间的窗口还必须定义清楚。

因此普通菜单通常选择可观测、可恢复的最终一致；支付确认、剩余库存判断、刚写入后必须看到最新状态等请求，应走事实存储或明确保证读到所需版本的路径。不要为了“所有读都必须缓存命中”引入无法验证的复杂协议。

### 删除哪些 key，也是一致性的一部分

菜品价格变化可能影响详情、菜单列表、搜索结果和活动页。如果只删除详情 key，列表仍可能旧。

为每个写操作维护明确的失效映射：

```text
菜品修改 → 菜品详情 key + 所属菜单版本/列表 key
活动规则修改 → 活动版本 + 相关价格计算缓存
权限修改 → 权限版本 + 授权结果缓存
```

批量视图可以采用版本化命名空间，但要考虑版本读取成本、旧空间回收和版本更新的可靠性。失效事件还需处理重复、乱序和积压；消费者删除失败必须有可追踪的重试记录。


### 缓存穿透：查询的对象根本不存在

不断请求不存在的菜品，缓存每次未命中，数据库每次也查不到。

处理顺序通常是：校验 ID 格式与访问权限，限制异常流量；对确认不存在的结果做短期负缓存；必要时使用 Bloom Filter 拦截明显不存在的 ID。

负缓存应该是可区分的状态，例如 `{status: "NOT_FOUND"}`。数据库超时和服务失败不能写成“不存在”，否则会把临时故障变成错误业务结论。新增对象后需失效负缓存，并处理过滤器同步。

### 缓存击穿：一个热门 key 失效

假设某菜单每秒 5000 次请求，数据库读取需要 100 毫秒。在未合并并发的情况下，一次缓存失效窗口就可能出现约 500 个重叠回源请求。

**Singleflight 的原理**是同一进程中相同 key 的并发请求共享一个正在执行的加载任务。10 个应用实例仍可能各自回源一次；是否值得增加跨实例协调，要根据数据库预算判断。

分布式重建锁可以进一步减少回源，但需要：拿锁后再次检查缓存；等待者有超时；锁失败时不无限自旋；Redis 故障时仍有本地并发限制；加载失败不写错误值。

允许短暂旧数据时，可以存储逻辑过期时间：逻辑过期后继续返回旧值，由单个任务异步刷新。还应有最大可陈旧时长及物理回收期限，避免刷新长期失败却一直返回旧数据。

### 缓存雪崩：大量 key 或整个缓存层同时失效

常见触发包括统一 TTL、实例故障、误清理、冷启动，以及扩容后缓存分布变化。

TTL 加随机抖动只能缓解同时过期。缓存实例不可用时，更重要的是保护数据库：按业务设回源并发上限、排队长度、超时和拒绝策略；允许的读请求使用有界本地旧缓存。

假设总读 QPS 为 2 万，命中率从 99% 降为 90%：

```text
原回源 QPS：20000 × 1% = 200
新回源 QPS：20000 × 10% = 2000
```

命中率只下降 9 个百分点，数据库压力却变为 10 倍。命中率还应结合流量绝对值和回源成本观察。

### 一个可执行的读取策略

以下是应用层伪代码，重点在状态和预算，不绑定某个 Java 客户端。

```text
getDish(tenant, dishId):
    authorize(tenant, dishId)
    key = buildKey(tenant, dishId, schemaVersion)

    cached = cacheGetWithDeadline(key)
    if cached is valid:
        return decode(cached)

    return localSingleflight(key, deadline, () -> {
        second = cacheGetWithDeadline(key)
        if second is valid:
            return decode(second)

        if !dbBulkhead.tryAcquire():
            return allowedStaleValueOrBusy()

        try:
            row = databaseReadWithDeadline(tenant, dishId)
            payload = row exists ? VALUE(row) : NOT_FOUND
            ttl = row exists ? baseTtl + boundedJitter : shortNegativeTtl
            bestEffortCacheSetWithDeadline(key, payload, ttl)
            return payload
        finally:
            dbBulkhead.release()
    })
```

这里刻意保留三个不同结果：缓存未命中、数据库确认不存在、下游调用失败。缓存回填失败不必让已经成功的数据库读取失败，但应计数并告警。该流程仍采用最终一致，未声称消除前文分析的旧回填竞态。

## 分布式协作：锁、幂等与限流


### 锁的基本协议为什么需要唯一 token

```redis
SET demo:lock:menu:20 unique-attempt-token NX PX 5000
```

`NX` 保证仅在 key 不存在时设置，`PX` 把租约与创建放在同一命令中，token 用来识别这次持有者。

解锁必须原子比较 token 再删除：

```lua
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
end
return 0
```

不能先 `GET` 再独立 `DEL`：两条命令之间旧锁可能到期，新持有者已经取得锁，此时会误删新锁。

这套获取与释放协议的前提和限制见 [Redis 分布式锁文档](https://redis.io/docs/latest/develop/clients/patterns/distributed-locks/)。

### 正确解锁仍无法阻止过期持有者继续操作

```text
A 拿到 5 秒锁
A 因 GC 或调度暂停 8 秒
锁在 Redis 中过期
B 拿到新锁并更新资源
A 恢复运行，继续按旧状态写资源
```

Redis 无法让暂停中的应用线程在租约结束时自动停止。续租能降低任务超过租约的概率，无法让网络分区、暂停和失联消失。

Fencing token 的思路是给持有者分配递增序号，实际资源写入端拒绝旧序号。例如资源已接受 42，之后拒绝 41。检查必须在资源端与写入原子完成，而且序号生成机制必须满足故障下的单调性；不能忽略异步复制回退后 `INCR` 序号复用的问题。

因此，缓存重建锁可按减少重复工作的目标设计；资金、库存等正确性仍由数据库条件更新、唯一约束或满足所需一致性的协调协议保护。

### 幂等回答的是“重试是否重复产生结果”

锁处理同时执行；幂等处理重复执行。请求可能隔一分钟再次到达，此时早已没有锁，但仍不应该产生第二张订单。

建议在事实存储中建立：

```text
唯一键：(tenant_id, idempotency_key)
请求摘要：同一 key 是否用于不同请求
状态：PROCESSING / SUCCEEDED / FAILED
业务结果：order_id 等
```

去重记录和业务写入尽量在同一数据库事务内完成。外部支付等副作用继续使用对方支持的幂等协议和结果查询。

Redis 可以作为快速去重层，但 key 到期、淘汰或故障丢失后，数据库约束仍需有效。超时表示结果未知，应按原幂等键查询或重试，不能每次生成一个新键。

### 限流的原理与选择

| 算法 | 原理 | 优点 | 代价与边界 |
| --- | --- | --- | --- |
| 固定窗口 | 对时间窗口内请求计数 | 状态少、实现简单 | 窗口边界附近可能集中通过两倍额度 |
| 滑动日志 | ZSet 保存窗口内每次请求时间 | 窗口统计较精确 | 状态量随请求数增加，清理成本必须受控 |
| 滑动计数 | 加权统计相邻时间桶 | 空间较少 | 是近似统计 |
| 令牌桶 | 随时间补充令牌，请求消耗令牌 | 允许受控突发 | 必须原子更新余额与时间 |
| 漏桶 | 以固定速率排出积压请求 | 平滑下游负载 | 需要队列上限和等待超时 |

令牌桶的核心公式是：

```text
available = min(capacity, oldTokens + elapsed × refillRate)
若 available >= cost：扣除 cost 后放行
否则：拒绝或计算等待时间
```

在多应用实例下，读取余额、计算补充、判断和扣减必须作为一次原子操作。时间源要统一，并定义时钟回退时的处理；使用服务端时间也不能假设墙上时钟永不跳变。

固定窗口常见错误是先 `INCR`，再单独 `EXPIRE`，进程在中间崩溃留下永久计数器。可用短 Lua 合并；通常仅首次创建时设窗口有效期，每次刷新 TTL 会改变算法语义。

对于模型调用，RPM、TPM 和并发数是不同限制：令牌桶限制单位时间预算，并发槽控制正在执行的请求数；TPM 可先预留估算量，再按实际用量结算，还要处理取消和超时后的预留回收。

Redis 不可用时选择放行还是拒绝，要按业务定义。高成本付费调用不能因为限流层故障就无限放行；低风险查询则可能使用本地保守限流继续服务。

## 故障后的数据：持久化、复制与集群


### RDB：保存某个时间点的数据快照

RDB 将某个时间点的数据集序列化为文件。后台保存通常通过子进程执行，父进程继续处理请求。

`fork` 后父子进程开始时共享内存页；父进程修改页面时，操作系统通过写时复制保留子进程所需的旧内容。这样得到一致快照，但频繁写入会产生额外页面与内存开销，创建子进程本身也可能造成停顿。

RDB 适合紧凑备份和整库恢复；崩溃恢复时，快照之后未保存的变化可能丢失。不要把“后台保存”理解为没有 CPU、磁盘或内存成本。

### AOF：追加记录可以重放的写入

AOF 记录用于恢复状态的写操作。需要区分内存状态、AOF 缓冲、操作系统页缓存和持久介质。

- `always`：更频繁地同步落盘，通常提供更强持久化保证，但延迟与吞吐代价更高。
- `everysec`：通常约每秒同步一次，常见丢失窗口约一秒；严重 I/O 故障、同步延迟或相关配置会影响实际边界。
- `no`：由操作系统决定刷盘时机，窗口更不可控。

AOF 重写根据当前数据集生成更精简的恢复表示，而不是简单把旧日志压缩一遍。现代版本可以使用多部分 AOF 与 RDB 格式的基文件，恢复和备份时应遵守对应版本的文件与清单规则。

RDB 与 AOF 可以结合使用。恢复速度、备份大小和可接受数据丢失需要一起验证。[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

### 四种“成功”不要混淆

```text
客户端收到成功
≠ 所有副本已收到
≠ 写入已在目标节点持久落盘
≠ 故障切换一定选中包含该写入的副本
```

应用超时也不意味着写入没执行：命令可能已生效，只是响应未到达。对会产生累积效果的操作，重试策略与幂等设计必须配套。

备份要在隔离实例上实际恢复，记录耗时，抽查关键数据，并确认依赖文件完整。备份文件存在本身不能证明恢复目标达成。


### 主从复制为什么可能丢写

Redis 常见复制是异步的。主节点执行写入后向副本传播，客户端可能在副本收到之前就收到成功。

```text
客户端写 x=2
主节点执行并返回成功
主节点在副本收到前故障
副本晋升，仍保存 x=1
```

复制提高冗余和恢复能力，但这条时序说明它不自动提供零数据丢失。

### 全量同步、部分同步和复制积压缓冲区

新副本或无法续接的副本通常需要全量同步基线，然后接收同步期间产生的增量。

短暂断连后，副本利用复制标识和偏移量请求续传。主节点的 backlog 保存最近一段复制数据；所需区间仍在缓冲中且复制历史兼容，才有机会部分同步。

backlog 是按字节覆盖的历史窗口，可按如下方式初估：

```text
backlog 容量 ≈ 峰值复制字节速率 × 期望覆盖的断连时长 × 裕量
```

例如复制流量每秒 10 MB，期望覆盖 60 秒断连，仅数据量就约 600 MB，还需留波动空间。应测复制字节量，而非只看命令 QPS。[复制机制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

### WAIT 能增强什么，不能保证什么

`WAIT` 等待当前连接此前写入被指定数量副本确认，返回实际确认数。应用必须检查返回值；超时或数量不足不撤销已经完成的写入。

它降低故障丢写概率，但不会把 Redis 变成强一致系统，也不等于等待副本持久落盘。若跨连接调用，不能默认等待的是另一个连接此前执行的业务写入。[WAIT](https://redis.io/docs/latest/commands/wait/)

涉及本地及副本 AOF 同步确认，可评估 Redis 7.2 起的 `WAITAOF`，但仍需检查实际返回值、配置与故障切换协议。[WAITAOF](https://redis.io/docs/latest/commands/waitaof/)

### Sentinel：发现故障并协调主从切换

Sentinel 负责监控、故障判断、故障转移协调和向客户端提供主节点信息；它不负责把业务数据分片，也不是普通读写流量必经的代理。

单个 Sentinel 判断不可达属于主观判断；足够 Sentinel 同意后形成客观下线判断。实际发起故障转移还涉及选举与多数授权，不能把配置 quorum 和多数授权混为一谈。

通常部署至少三个 Sentinel，并分散到独立故障域。三个进程全在一台机器上，无法应对整机故障。客户端必须支持发现新主、重连和恰当重试。

网络分区下旧主可能暂时继续接受部分客户端写入；限制最低副本数量及延迟可以降低风险，但不是严格一致性的替代。[Sentinel](https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/)

### Cluster：16384 个槽如何把数据分散到节点

Redis Cluster 通过 hash slot 将 key 分配给主节点。典型计算为：

```text
slot = CRC16(key) mod 16384
```

客户端维护槽到节点的映射，并处理拓扑变化。`MOVED` 通常表示应更新目标位置认知；迁移过程中的 `ASK` 表示本次请求需要临时到指定节点并遵循对应协议。

Hash tag 允许相关 key 使用大括号内相同内容计算槽：

```text
stock:{tenant-7:sku-1001}
reservation:{tenant-7:sku-1001}:request-88
```

这样可以支持同槽多 key 操作。但如果所有 key 都使用 `{tenant-7}`，大租户的数据和流量会集中到一个槽。应按需要原子操作的最小业务单元选择 tag。

Cluster 扩容是在迁移槽与 key，一个巨大 key 仍归一个分片；它不会把单个 Hash 或 ZSet 的成员自动拆开。[Cluster 规范](https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/)

### 怎么选择部署方式

| 需求 | 常见起点 | 仍需解决 |
| --- | --- | --- |
| 本地学习与验证 | 独立实例 | 不具备自动故障转移 |
| 单主容量足够，需要自动切换 | 主从 + Sentinel，或相应托管服务 | 异步复制丢写窗口、客户端恢复 |
| 数据容量或流量超过单主承载 | Cluster，或有分片能力的托管服务 | 同槽约束、热点、迁移和容量倾斜 |
| 业务必须严格防重复、防超卖 | 事实存储约束与完整协议 | 不能只靠升级 Redis 部署规模实现 |

从副本读取可能看见旧状态。刚写入后的读取、锁状态和关键判定，应使用满足所需可见性保证的路径；“读写分离提升性能”必须伴随一致性取舍。

## 消息如何可靠处理：Pub/Sub 与 Streams

### 消息机制：Pub/Sub 与 Streams 的可靠性差在哪里

Pub/Sub 将消息即时推送给当前订阅者，不保存可供断线消费者重放的历史。适合允许丢失的即时通知；断线期间的消息不能依靠重新订阅恢复。[Pub/Sub 投递语义](https://redis.io/docs/latest/develop/pubsub/)

Streams 将消息保存在流中，消费组维护投递与待确认状态：

```text
XADD 写入消息
→ XREADGROUP 投递给消费者
→ 消息进入待确认列表 PEL
→ 完成业务处理
→ XACK 确认
```

```redis
XGROUP CREATE demo:orders demo:billing 0 MKSTREAM
XADD demo:orders * event_id evt-1001 order_id order-1001
XREADGROUP GROUP demo:billing worker-1 COUNT 10 STREAMS demo:orders >
```

处理业务后，用读取结果中的实际消息 ID 执行 `XACK`。消费者崩溃时，可检查 `XPENDING`，通过 `XAUTOCLAIM` 等方式接管超时待确认消息。

如果业务已经提交但 ACK 前崩溃，接管者会再次处理。因此消费组不提供业务层 exactly-once；仍需要事件 ID 去重，并把去重和业务写入放在同一事务边界。

`XACK` 移除待确认状态，不等于从流中删除消息。流需要保留与裁剪策略，裁剪过早可能删掉尚待处理的内容。可靠性还受 Redis 持久化、复制、消费者恢复和积压容量共同影响。[Redis Streams](https://redis.io/docs/latest/develop/data-types/streams/)

## 生产实践：性能、客户端、排障与验收


### BigKey 大在体积或元素数量

BigKey 可能是一个很大的 String，也可能是有大量成员的集合。

影响包括：更长执行时间、大响应占用网络、大对象分配与释放、复制与迁移变慢。没有适合所有业务的固定阈值，应同时规定单 value 字节数、集合成员数、单次返回字节数与耗时预算。

治理优先级：改变数据模型、按业务维度分桶、分页、只读必要字段、限制返回条数。删除大型复合对象时，可以评估 `UNLINK` 将主要回收工作交给后台；它不是无限免费，仍需观察后台释放队列与内存峰值。[UNLINK](https://redis.io/docs/latest/commands/unlink/)

### HotKey 热在请求集中

一个 100 字节 key 也可能每秒被读几十万次，压满一个分片。扩容其他分片并不能改变它仍由一个节点承载的事实。

读热点可考虑短 TTL 本地缓存、请求合并、CDN 或明确容忍旧读的副本分摊。多级缓存会增加一致性复杂度，需要定义各层 TTL、版本和失效传播。

写热点可以按桶分散计数并异步聚合，但代价是即时精确汇总和全局原子性减弱。不能一边拆分计数，一边仍声称每次读都是全局精确值。

### SCAN 为什么比 KEYS 温和，却不是免费快照

`KEYS` 在大键空间中做全量匹配，会占用执行时间。`SCAN` 用游标分批推进，把一次长工作分散到多次调用。

但 `COUNT` 是工作量提示，不保证返回条数；遍历中可能重复返回，增删数据时不是一致性快照。完整遍历仍需处理整个键空间，游标回到 0 才结束。

```redis
SCAN 0 MATCH demo:dish:* COUNT 100
```

后续使用返回的游标继续。清理任务需幂等、限速；Cluster 的完整遍历还需要覆盖相关主节点，不能只扫描一个节点。[SCAN 保证与边界](https://redis.io/docs/latest/commands/scan/)


### 连接不是越多越好

复用长连接，避免每次请求建连。是否需要连接池、池应多大，取决于客户端模型：同步阻塞连接、异步复用连接、事务、阻塞消费可能需要不同策略。

事务上下文和长时间阻塞操作应避免占住共享业务连接。异步客户端的 I/O 回调线程不应执行耗时数据库查询或复杂业务计算，否则服务端很快，客户端也会积压。

### 超时应服从总请求预算

一次接口若预算为 200 毫秒，缓存连接、命令、重试、数据库回源不能分别各等 200 毫秒。

定义整体 deadline，将剩余时间传给各阶段。重试应有次数、退避、抖动及幂等约束；缓存故障时无条件大量重试会放大连接风暴。

### key 与序列化是长期接口

建议包含环境、服务、租户、实体标识和 schema 版本：

```text
prod:menu:tenant:7:dish:1001:v2
```

不要让不同租户共享同一个业务 key。RAG 检索缓存还应包含知识库版本、权限范围或权限版本、查询归一化策略和模型相关版本；缓存命中不能跳过授权。

Value 应定义格式、字段默认值和演进策略。避免把难以跨语言或跨版本兼容的应用对象序列化格式当作永久契约。缓存载荷尽量只包含展示所需字段，敏感数据按业务要求最小化。

### 安全配置也是可用性设计

使用受控网络、身份认证和最小权限 ACL；按需要启用 TLS。应用身份只获得所需命令与 key 范围，不应拥有随意清库和更改配置的权限。

日志与监控避免输出口令、令牌或完整敏感 value。线上诊断需要考虑命令成本，不能把 `MONITOR` 长期开在高流量实例上。[Redis ACL](https://redis.io/docs/latest/operate/oss_and_stack/management/security/acl/)

### 常见故障：按证据区分原因

| 现象 | 优先检查的证据 | 常见原因与处理方向 |
| --- | --- | --- |
| 应用 Redis 超时，慢日志很少 | 应用连接等待、网络 RTT、响应字节数、应用 GC | 网络或客户端排队；慢日志不覆盖全部端到端时间 |
| 单个分片 P99 高 | 每节点 CPU、热点分布、命令耗时 | HotKey、慢 Lua、大范围命令；限制单次工作并治理热点 |
| 命中率下降且数据库 QPS 上升 | TTL 分布、淘汰速率、部署时间线 | 集中过期、容量不足、冷缓存；限流回源并分批预热 |
| Redis 写入 OOM 错误 | maxmemory、策略、可淘汰 key、缓冲占用 | 配额与策略不匹配；识别可删数据后调整容量与模型 |
| 容器被 OOM Kill | 容器内存、RSS、fork 时间点、写入速率 | 实际用量超容器限制；降低数据上限并留后台任务裕量 |
| 后台保存时延迟突增 | fork 耗时、COW 内存、磁盘时延 | 快照或重写资源竞争；按证据优化内存与 I/O |
| 副本反复全量同步 | backlog 覆盖、网络断连、复制吞吐 | 无法续接导致同步循环；修复网络并按字节预算配置 |
| 锁仍出现并发执行 | 租约、应用暂停、续租、主从切换 | 租约结束或状态回退；资源端保护最终正确性 |
| 菜品更新后仍显示旧价格 | DB 提交、DEL、读请求和回填时间线 | 旧回填、遗漏失效、副本旧读、多级缓存未清理 |
| Streams 积压增长 | 最老 pending 年龄、消费者活性、重试记录 | 消费者崩溃、业务失败、未接管消息；恢复并控制重试 |

常用只读观察入口：

```redis
INFO memory
INFO stats
INFO commandstats
INFO persistence
INFO replication
SLOWLOG LEN
SLOWLOG GET 20
LATENCY LATEST
```

`SLOWLOG` 主要记录命令执行时间，不包含全部客户端等待和网络传输；延迟事件是否可见还取决于配置。诊断时按时间窗口比较增量，不要只看自启动以来累计值。[SLOWLOG GET](https://redis.io/docs/latest/commands/slowlog-get/)

一次菜单接口变慢，可按以下顺序缩小范围：

1. 用 Trace 分离缓存调用、连接等待、数据库回源和序列化时间。
2. 判断是全部节点慢、单分片慢，还是少数业务 key 慢。
3. 对齐命令耗时、响应大小、CPU、内存、复制和持久化时间线。
4. 若 Redis 并不慢，继续查客户端线程、连接和网络；若数据库慢，先检查命中率与回源增量。
5. 一次只验证一个主要假设，确认指标恢复后再扩大调整。


### 内存预算

```text
数据内存 ≈ key 数 × 平均每 key 实际占用
         + 大集合与索引开销

进程/容器预算还需考虑：
客户端缓冲 + 复制/AOF 缓冲 + 分配器碎片
+ 后台保存写时复制 + 操作系统与其他进程空间
```

应使用 `MEMORY USAGE` 抽样和真实数据装载来估计，不能只把 JSON 字节数相加。主从副本会增加部署总内存，分片不均也要求单节点保留余量。

### 带宽预算

假设平均响应 10 KB，每秒读取 2 万次：

```text
仅响应载荷约为 200 MB/s，约 1.6 Gbit/s
```

这还没计入协议、请求、复制等开销。此时即使命令本身便宜，网络也可能先饱和。减少缓存对象与读取字段往往比单纯增加 CPU 更有效。

### 压测必须覆盖失败场景

验收至少包括：真实 key/value 大小与热点分布；稳定态 P50/P95/P99；冷启动和热点失效；短暂断连与主从切换；持久化期间写入；容量接近上限；客户端超时重试；数据库回源限流。

三个场景尤其值得手工验证：在“数据库读出旧值、缓存回填前”暂停请求，触发并发更新，检查旧回填是否符合预期；把锁持有者暂停到租约过期再恢复，验证业务资源是否拒绝过期操作；模拟写入成功但响应丢失，按原幂等键重试，确认只产生一个业务结果。

本文代码为教学示例，未在本地 Redis 实例执行；上述实验属于建议验收项，不能当作已完成的测试结果。

## 用机制判断方案：常见误区与参考资料

### 常见说法和实际边界

| 常见说法 | 更准确的理解 |
| --- | --- |
| Redis 是单线程，所以不会并发出错 | 核心命令串行不等于客户端多步业务原子 |
| Redis 很快，所以可以返回整个集合 | 复杂度、结果数量与传输字节数都决定成本 |
| Pipeline 可以保证批次原子 | 它主要减少网络等待 |
| Lua 出错会全部回滚 | 原子执行不等于错误回滚 |
| 设置 TTL 后会准时触发任务 | 过期不提供精确可靠的业务调度 |
| maxmemory 就是进程最大内存 | 内存统计口径与额外开销不同 |
| 提交数据库后删缓存就完全一致 | 仍存在旧回填、失效失败、旧副本读取等窗口 |
| TTL 加随机值就能防雪崩 | 它只缓解集中过期，实例故障还要控制回源 |
| 加了锁就能保证幂等 | 锁限制并发，幂等限制重复结果 |
| 有续租就不会出现两个持有者执行 | 暂停、失联和故障切换仍可能破坏业务互斥 |
| WAIT 等于强一致或落盘保证 | 它等待副本确认，必须检查数量且理解故障边界 |
| Cluster 会自动解决所有热点 | 一个 key 仍由一个分片承载 |
| 消费组保证消息只处理一次 | 提交成功但 ACK 失败会导致重复处理 |
| 慢日志没有记录说明 Redis 链路没问题 | 客户端排队、网络和大响应可能不体现在慢日志中 |

Redis 的工程价值有两面：常见数据操作可以在内存中完成，多个应用实例也能共享短小、边界明确的原子状态。至于数据能陈旧多久、失败怎样恢复、哪些不变量必须由事实存储保护，仍由应用设计负责。

把这些边界放回请求链，类型选择、缓存一致性、锁、限流和高可用就不再是零散的命令题，而是不同位置上的取舍。
