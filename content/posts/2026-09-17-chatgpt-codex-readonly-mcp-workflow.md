让 Codex 改几行代码不难。麻烦的是，你可能还不知道该改哪里。

比如模型调用费用涨了。是流量变多了，还是重试太频繁？缓存没命中，是键设计有问题，还是请求本来就很难复用？这些问题得翻代码、查日志，有时还要找出当初那个 PR，看看为什么这么写。

数字生命卡兹克在一篇 X 文章里分享了自己的做法：把这段分析工作交给 ChatGPT，等方案出来，再让 Codex 改代码。[1]

这个分工很好理解，但有个绕不开的问题：ChatGPT 看不到生产数据，凭什么判断哪里值得改？他的办法是给业务系统加一个只读 MCP 服务。

## 先让 ChatGPT 看见系统到底怎么跑

作者当时在给 AIHOT 降成本、调性能。GitHub 插件能提供代码和 PR 历史，却给不了每天的实际调用量、费用分布和缓存命中率。

代码里写了缓存，不等于生产环境里缓存就有效。某段逻辑看着复杂，也未必值得花时间优化。没有运行数据，模型很容易给出一堆看起来都对、却排不出优先级的建议。

于是，他让 Codex 开发一个只读 MCP Server，把业务数据查询能力接出来，并接上已有的飞书认证，限制访问账号。之后在 ChatGPT 中同时选择这个业务插件和 GitHub 插件，让模型边看代码边查数据。方案做好，再交回 Codex 实施。[1]

在这个过程中，PR 历史也有用。有些看起来多余的处理，可能是为了解决过去出现过的故障。知道当初为什么加上它，才好判断今天能不能删。

## MCP 负责取数，接口要做得具体

这里可以把 MCP 理解为连接 ChatGPT 和业务系统的查询通道。模型调用工具，服务端检查权限和参数，查出允许访问的数据，再把结果交回来。

```text
ChatGPT 查询费用、缓存或错误信息
        ↓
只读 MCP 服务检查身份、权限和查询参数
        ↓
从指标系统、日志汇总或数据库只读视图取数
        ↓
返回结果，附上时间范围和统计口径
        ↓
ChatGPT 结合代码出方案，Codex 接着实施
```

如果自己做这类服务，可以从几个明确的业务查询开始。下面是接口设计示例，不是原作者公开的实现：

| 工具示例 | 返回内容 |
| --- | --- |
| `get_cost_breakdown` | 按模型、业务环节拆分的费用和调用量 |
| `get_cache_metrics` | 缓存命中、未命中、失效和回源统计 |
| `get_error_summary` | 各类错误的数量和脱敏样例 |
| `get_latency_summary` | 指定接口或环节的耗时分布 |

返回数字时，把采集时间、时区、过滤条件也带上。费用是估算的，还是账单里的实际金额？当天数据有没有收齐？这些信息缺了，模型可能拿着两个口径不同的数字推理半天。

接入方式有官方支持。OpenAI 的 Developer mode 文档列出了远程 MCP、SSE、streaming HTTP 和 OAuth。查阅时，可以从 Settings → Security and login 开启 Developer mode，再到 Plugins 创建应用，在会话里选用。[2]

这里需要的是 ChatGPT 能访问的远程服务。只在本机装好 stdio MCP，再填一个本地路径，还接不通。菜单位置和账号能用哪些功能，以实际界面为准。

## 拿“降低模型费用”走一遍

下面用一个假设的缓存优化任务说明流程，不代表 AIHOT 的实际诊断结果。

先让 ChatGPT 查最近一段时间的调用分布、输入输出 token、失败重试和缓存情况，再找到对应的代码入口。假如某类请求重复得很多，就继续查：这些请求的结果能不能共用？能保留多久？有没有必须实时计算的情况？

查到这一步，才有足够依据讨论缓存键和失效规则。否则一句“加缓存”，可能省下了调用费，却让用户拿到了过期结果。

交给 Codex 的任务也就具体了：在哪个入口加缓存，哪些条件下绕过缓存，数据变化后怎么失效，以及用什么测试证明结果没有出错。

做完还得看效果。除了总费用，也要比较每次成功请求的平均费用、流量和错误率。如果当天请求量少了一半，账单下降并不能说明优化有效。前后用同一套统计口径，才知道这次修改究竟省了什么。

## 方案要能接着做，别让 Codex 从头猜

这套分工最容易浪费时间的地方，是交接。

ChatGPT 写了很长的分析，最后只剩一句“建议增加缓存、优化重试”。Codex 收到后，还是得重新找调用入口、查运行情况。前面那轮分析就没省下多少工作。

交接文档可以短，但要带上足够的信息：

```text
任务：降低某业务环节的重复模型调用

目标：希望改善什么，哪些行为和时效要求必须保留。
依据：查询结果、时间范围、统计口径、代码版本、文件位置和相关 PR。
疑问：哪些已经查实，哪些还只是猜测，缺什么数据。
改法：修改哪些模块，先后顺序是什么，有哪些依赖。
验收：运行哪些测试，比较哪些指标，怎样判断结果正确。
回滚：出现什么情况要停，如何恢复，需要保留哪些观测数据。
```

代码版本和数据时间尤其容易漏。出方案之后仓库可能又有了改动，Codex 需要核对差异；仍然有效的查询结果则可以直接沿用。

给 ChatGPT 的提示词可以这样写：

```text
结合项目代码、近期 PR 和最近 7 天的业务指标，查清主要成本来源。
每个判断都附上依据。还没查实的地方请明确标出来，缺数据就继续查。

按预期收益、工作量和风险排列优化建议，写清要改的模块、
修改方向、测试方式、验收指标和回滚条件。

最后整理成一份 Codex 能接着执行的任务清单，附上代码版本和数据时间。
```

交给 Codex 时，可以接着说：

```text
检查这份方案是否符合当前代码和运行情况，再实施值得做的优化。
已有证据能用的直接复用，有冲突或过时的地方再查，不必从头调研。

逐项修改并运行相关检查，说明改了什么、验证了什么、还剩哪些问题。
准备部署和回滚步骤。需要上线后才能确认的收益，请单独列出。
```

原作者在 Codex 的快速聊天中使用 ChatGPT，再点“添加到 Codex”移交会话。[1] 本文没有复现这组界面操作。如果找不到这个入口，把方案保存成 Markdown 交过去也可以。

## “只读”要靠权限，不靠一句提示词

原作者要求服务只读、最小权限、可审计，同时不能暴露敏感数据。这些限制都需要在服务端实现。

接好 OAuth 后，还得检查当前账号能看哪些业务数据。数据库账号、查询视图和接口权限也要跟着收紧。即使模型发起了不合适的请求，服务端也应该能拦住。官方文档里的 `readOnlyHint` 是工具行为标记，不能代替这些权限。[2]

读操作也会消耗资源。一次大范围日志扫描或复杂聚合，就可能拖慢生产系统，所以查询要有时间跨度、条数、并发和超时限制。经常要看的数据，可以提前聚合，或从只读副本查询。

返回什么同样需要控制。密钥、完整用户记录和无关的原始日志，不该因为接口只读就直接送出去。

## 先试一次，再决定要不要搭服务

如果只是偶尔分析一个问题，可以先导出脱敏报表，连同必要代码和近期修改说明一起交给 ChatGPT。等它确实能据此写出有用的方案，再考虑把取数过程做成 MCP。

频繁查数据时，MCP 才更省事。尤其是模型看完第一轮结果，还要继续查某个环节、某段时间的数据，接口能减少来回导出和上传的工作。

至于能省多少 Codex 额度，原文提供的是作者自己的使用体验，没有可重复的对照实验。文中的具体模型、套餐次数和额度分离规则，本次也没有拿到对应的官方确认，不能直接套到每个账号上。[1]

找一个范围小、指标清楚的任务试试就够了。记下两边花的时间和工具用量，也看看 Codex 有没有重新调查、返工。如果方案拿过来就能继续做，这个分工才真正帮上了忙。
