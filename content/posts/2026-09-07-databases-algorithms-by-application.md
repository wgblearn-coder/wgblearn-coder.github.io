查最近订单要建索引，算畅销菜品要做 Top K，通知厨房还要排队和重试。同一笔订单走过这些环节，数据库和算法其实一直在配合，只是在教程里经常被分开讲。

下面用餐饮 SaaS 中的一笔订单 O102 串起这些选择，它属于租户 T31。用户先查菜单，再提交订单；服务校验库存、拦住重复请求，后台更新搜索和经营统计，最后安排通知。数据量小时，很多实现都能工作。流量上来以后，查多少行、占多久锁、重试会不会重复扣库存，就会决定这条流程能否撑住。

文中的数据量、租户数和 QPS 都是推演假设，不是生产实测。实际选型还得回到访问日志、慢查询、锁等待和业务对账，确认瓶颈确实存在。

## 一笔订单会遇到哪些数据问题

同一个“订单系统”包含多种完全不同的工作负载。按 `tenant_id` 查询某租户最近订单，需要稳定路由和时间索引；创建订单需要原子写入和幂等；“最畅销的前十道菜”需要聚合和 Top K；Agent 工作流则更像一个带依赖和重试状态的任务图。这些请求需要的结构各不相同。

| 应用场景 | 数据库主要机制 | 配套算法/结构 | 常见复杂度（典型实现） | 适用边界 |
| --- | --- | --- | --- | --- |
| 查询与检索 | 组合索引、覆盖索引、读一致性、搜索派生库 | 哈希表、B+树、二分、双指针 | 点查平均 `O(1)`；B+树约 `O(log n)`；有序归并 `O(m+n)` | 哈希不适合范围查询；跨分片广播应受控 |
| 可靠写入 | 唯一约束、事务、MVCC、条件更新、幂等键 | 内存哈希判重、状态机 | 内存哈希平均 `O(1)`；数据库树索引约 `O(log n)`；事务成本依赖索引、锁和日志 | 幂等不等于全局 ID；长事务会放大锁和冲突 |
| 缓存与限流 | Cache Aside、TTL、热点保护、令牌桶 | LRU、哈希表、双向链表、滑动窗口 | LRU 读写 `O(1)`；窗口维护 `O(1)` 均摊 | 缓存不是事实来源；分布式限流需要共享状态 |
| 统计与排序 | 聚合索引、CDC/Outbox、OLAP 派生 | 堆、排序、前缀和 | Top K `O(n log k)`；完整排序 `O(n log n)`；前缀和查询 `O(1)` | 只要 Top K 不必全量排序；实时性与成本需权衡 |
| 任务调度 | 任务表、租约、重试状态、消息队列 | 优先队列、队列、拓扑排序、BFS | 入队/出队 `O(log n)`；DAG 遍历 `O(V+E)` | 拓扑合法不代表执行可靠，还要处理重试和幂等 |
| 分片与扩容 | 虚拟桶、路由 epoch、副本、CDC 迁移 | 哈希映射、归并、游标分页 | 路由平均 `O(1)`；每片候选归并约 `O(k log s)` | 分片解决容量和写吞吐，复制解决可用性，备份解决回溯 |

选型时，可以先问结果是否需要有序。要按时间翻订单，树索引通常比哈希结构合适。接着看哪些状态必须一起提交，以及请求能否带上分片键：这会影响事务能否留在单片内，也决定查询是否需要跨片聚合。

## 查菜单和历史订单，索引怎样建

用户打开门店页面，先按 `tenant_id`、`store_id` 查可售菜品，再按订单号或时间查询历史订单。关系数据库中的 B+ 树适合这种“等值加范围”的访问：例如可以建立 `(tenant_id, store_id, created_at, id)` 组合索引，使数据库先定位租户和门店，再顺序读取时间范围。索引顺序要贴合过滤和排序条件；把大量低选择性的字段放在最前面，可能仍需扫描大量记录。

点查场景可以使用哈希表的思路：请求幂等键、订单号或缓存 key 映射到一条记录，平均查询接近 `O(1)`。但这是平均复杂度，哈希冲突和扩容仍需考虑；哈希表也不能自然支持“某时间段内的订单”这种范围查询。需要范围、排序或前缀匹配时，应优先使用有序索引、B+树或专门的搜索系统。

跨分片查询要把算法成本写出来。若按 `tenant_id` 分片，带租户条件的历史订单查询可以精确路由；没有分片键的手机号搜索，只能广播到所有分片，再由聚合层合并。

每片按稳定游标取 `k` 个候选，若要输出全部候选，归并成本约为 `O(sk log s)`；若只输出全局 `k` 条，可用小堆把归并控制在 `O(s + k log s)`，还要另算候选拉取成本。深分页使用大 `OFFSET` 会让每片重复扫描，宜改用 `(created_at, id)` 游标。

查询刚写入的订单时还要选择读副本。订单创建成功后立即展示、支付状态判断和库存校验，应该走 Leader 或具有读己之写保证的路径；允许延迟的经营报表才适合读取 Replica。否则会出现“下单返回成功，刷新却查不到”的复制延迟故障。验证时可以记录写入时间、读取节点、复制位点和用户可见时间，而不是只看 HTTP 200。

## 创建订单时，怎样守住库存和幂等

O102 的核心写入至少包含订单主表、订单明细、库存扣减和 Outbox 事件。只要这些数据共用 `tenant_id` 或 `store_id` 分片键，就能尽量落在同一分片，用一个本地事务完成。这些写入需要一起成功或回滚：订单不能只有主表没有明细，库存不能扣减成功而订单回滚，订单提交后必须留下待发布事件。

典型的库存条件更新如下：

```sql
UPDATE inventory
SET available = available - :quantity,
    version = version + 1
WHERE tenant_id = :tenant
  AND sku_id = :sku
  AND available >= :quantity
  AND version = :old_version;
```

应用检查影响行数是否为 1；`quantity` 应校验为正整数，`inventory` 还需有 `(tenant_id, sku_id)`（或再含 `store_id`）的唯一约束。

为 0 时，可能是库存不足，也可能是版本已被其他请求更新，需要重新读取并按业务返回。`version` 是乐观并发控制的一种表达；另一种是 `SELECT ... FOR UPDATE` 的悲观锁。前者冲突少时吞吐较好，后者适合必须串行保护的短临界区。无论哪种方式，都要缩短事务、固定访问顺序并监控锁等待和死锁，不能把“数据库支持事务”当成冲突自动消失。

MVCC 通过保存行版本，让读操作在一致性快照上工作，减少读写互相阻塞；它并不意味着所有并发写都自动安全。两个请求仍可能基于旧版本同时修改同一库存，必须依靠版本条件、唯一约束或锁来检测冲突。隔离级别也要与现象对应：不要看到脏读、不可重复读、幻读等名词就盲目提高隔离级别，因为更强隔离通常意味着更多等待和冲突。

客户端超时后重试是可靠写入最容易出错的地方。请求可能已经提交，只是响应在网络中丢失。客户端必须复用同一个 `(tenant_id, idempotency_key)`，数据库建立唯一约束，服务先查幂等记录或在同一事务中写入幂等结果。单机内存哈希只能快速判重，不能承担持久化幂等。未知结果时，应使用原幂等键查询原订单，而不是生成一个新订单号再试一次。全局 ID 解决碰撞，幂等键解决重复业务动作，两者职责不同。

Outbox 解决的是“本地提交成功但消息没发出去”的间隙。事务内写入订单和 Outbox，Publisher 再投递 MQ；消费者更新搜索、积分和统计时以业务键去重，并允许消息重复。订单是否成立由本地事务确定，搜索、积分和统计则靠消息与消费者逐步更新。只有参与者少、事务短且必须同时提交的场景，才值得评估 XA/2PC；长流程通常用状态机、Saga 或补偿动作表达。

## 菜单缓存与入口限流

菜单读取通常是高频读、低频改，适合 Cache Aside：先查缓存，未命中读数据库并回填；更新数据库后删除或刷新缓存。缓存项要带租户、门店和数据版本，避免不同租户命中同一 key。删除失败、并发回填和热点 key 都要设计处理方式，必要时用短 TTL、互斥重建或逻辑过期降低击穿压力。

单机 LRU 的经典实现是“哈希表 + 双向链表”：哈希表把 key 定位到节点，链表头表示最近使用，尾部表示最久未使用，因此读、更新和淘汰都能做到 `O(1)`。但算法题的 LRU 只解决淘汰顺序，真实系统还要处理穿透、击穿、雪崩、序列化大小和多实例一致性。Redis 等共享缓存能统一容量和限流状态，却增加网络故障和数据过期语义，仍不能替代数据库事实。

限流要先定义对象：按租户、用户、接口还是模型供应商限流。令牌桶允许一定突发，漏桶更强调平滑；滑动窗口可以精确统计最近时间段请求，但保存请求时间点的空间随流量增加。用固定窗口做快速保护时，要特别注意窗口边界的突发。限流计数成功后才执行业务，拒绝时返回可重试提示；重试策略还应配合退避和幂等，否则限流只能把重复压力推迟。

对 Agent 请求，缓存 key 还应考虑权限、知识库 revision、模型和工具版本。只按用户问题文本缓存，可能把一个租户的检索结果返回给另一个租户，也可能在权限变更后继续使用旧答案。验证缓存方案需要同时观察命中率、回源 QPS、过期后的正确性和权限隔离，而不是只看延迟下降。

## 畅销菜品 Top 10，是否需要全量排序

店长要看“今日各菜品销量 Top 10”。若每次打开页面都扫描订单明细并 `GROUP BY`，在线交易库会与报表争抢 CPU、IO 和锁资源。更稳妥的链路是订单事务写 Outbox，消费者或 CDC 更新统计表，报表从统计表或 OLAP 查询。派生数据允许延迟，就明确展示统计时间和延迟指标；需要刚提交订单立即计入的单店小查询，才在交易库做受控增量维护。

算法选择取决于结果规模。小数据或确实需要完整排行榜时，全量排序清楚直接，复杂度为 `O(n log n)`；大数据且只要较小的 Top K，可扫描数据并维护大小为 `k` 的最小堆，复杂度约为 `O(n log k)`，内存为 `O(k)`。新菜品销量更高时替换堆顶，最后再对 K 个结果排序。无论哪种方案，都要用 `(sales DESC, sku_id ASC)` 固定并列次序。

对于按天累加的金额或订单数，前缀和能把重复区间求和从 `O(n)` 降到 `O(1)`，代价是更新原始数据后需要重建或维护前缀结构。时间序列写入频繁、查询窗口多时，可在派生层按天或小时聚合；跨天查询再合并桶。统计链路必须有对账：从订单事实表抽样重算，与统计表按租户、门店和日期比较，发现差异后通过补偿任务重放事件。

## 订单提交后，通知任务怎样调度

订单创建后可能要发厨房通知、支付提醒、打印小票；Agent 也可能先检索，再调用工具，最后生成回复。普通队列适合先进先出和削峰，双端队列适合需要从两端处理的场景；需要按优先级或下一次重试时间取任务时，使用优先队列，入队和出队通常是 `O(log n)`。任务表中的状态、租约过期时间和尝试次数应持久化，避免进程崩溃后任务凭空消失。

工作流依赖可以建成 DAG。例如 `鉴权与权限范围确定 → 授权范围内检索 → 工具调用 → 汇总`，用 Kahn 算法按入度为 0 的节点逐步出队，时间复杂度是 `O(V+E)`。发现剩余节点无法出队，就说明有环。拓扑排序只回答“先后顺序”，不能回答工具超时怎么办、重试是否重复扣款、某节点部分成功如何补偿。执行器还需要每个节点的幂等键、超时、重试上限和人工介入状态。

一个具体失败是：消费者拿到“发送打印任务”，执行成功后在写完成状态前宕机，消息再次投递。若没有业务幂等键，厨房可能收到两张小票；若只依赖内存队列，重启后任务又可能丢失。可把 `order_id + task_type` 设为业务唯一键，执行前查询状态，外部系统支持时传入同一请求号；无法做到严格一次时，就把目标设计为“至少一次投递 + 幂等副作用”。验证应主动杀进程、重复投递和延迟 ACK，再检查订单、任务表和外部结果是否最终一致。

## 单库装不下以后，按什么分片

当单库容量、写吞吐、故障域或租户隔离成为明确瓶颈，才进入分片。餐饮订单常以 `tenant_id` 或 `store_id` 作为起点，让订单、明细、库存和 Outbox 共置；按 `order_id` hash 可能更均匀，却会让“查某租户最近订单”和库存事务失去精确路由。分片键不能只追求均匀，还要考虑查询携带率、事务边界和头部租户热点。

直接使用 `hash(tenant_id) % 分片数` 会给扩容留下麻烦。从 4 片扩到 8 片时，模数改变会让大量 key 改变归属。固定数量的虚拟桶更易迁移：先计算 `tenant_id → bucket_id`，再由路由表映射 `bucket_id → shard group`。

扩容选取部分桶，执行全量复制、CDC 追平、校验、短暂收口和原子切路由。路由带 `epoch`，源节点和目标节点都用 fencing 校验它，拒绝旧 epoch 的写；刷新拓扑后仍复用原幂等键。

每个分片通常是 Leader 加多个 Replica 的副本组。同步、半同步和异步复制分别在写延迟、RPO 与可用性之间取舍；读请求要按“是否允许陈旧、是否要求读己之写”分流。Leader 宕机后需要选主、刷新路由和恢复连接，任期、租约或 fencing token 用来阻止旧主继续写。复制副本不是备份：误删会被复制，备份和日志归档才能支持 PITR，恢复演练才能证明 RPO/RTO。

扩容和故障都必须用业务指标验收。除了容量、CPU、IO、复制延迟、锁等待、广播查询比例和迁移进度，还要对账重复订单、库存负数、订单与支付或统计的差异。迁移校验可以按桶统计行数和金额，再抽样比较主键、版本和校验和；切换后观察一段时间，确认读写流量、错误率和延迟稳定，再清理旧副本。

## 回到订单 O102

O102 到达 API 后，服务先校验租户、权限和幂等键。菜单查询按租户和门店路由，能命中缓存就直接返回；创建订单则在单分片事务中写主表、明细、扣库存并留下 Outbox。刚提交后的关键查询走 Leader，报表和搜索等消费者更新，厨房通知由持久化任务承接。容量不足时，再按虚拟桶迁移数据，用 epoch 和对账检查切换结果。

每个结构都服务于其中一个具体步骤。B+ 树减少扫描，堆避免为了 Top 10 排完整张榜，拓扑排序检查任务依赖。但复杂度解释不了所有问题：缓存查询即使是 `O(1)`，key 没带权限范围也会泄露数据；DAG 即使合法，打印任务缺少幂等也会重复出单。

设计落下来以后，还要试着让它出错：延迟副本复制，重复提交 O102，在通知发出后杀掉消费者，再核对订单、库存和小票。这样才能知道哪些保证由数据库承担，哪些仍然需要应用补上。
