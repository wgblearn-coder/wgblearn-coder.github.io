“昨天订单少了一份菜，帮我处理退款。”对话模型能理解这句话，也能写出得体的回复。可一旦要真的把钱退回去，问题就接连出现：订单在哪，适用哪版政策，已经退过多少，支付调用超时了怎么办？

从 Prompt、CoT 到 RAG、Agent，再到 SDD 和 Harness，这些方法分别处理其中一部分问题。有的改善模型的回答，有的补充资料和工具，还有的负责记住执行到了哪一步。把它们放回同一个退款任务里，比按名词逐个学更容易看出各自的用处。

下文选取截至 2026 年 9 月 7 日已核验资料中的代表性节点。退款场景、规则和金额均为教学示例，不代表真实公司的制度或生产成绩。SDD 指 Spec-Driven Development，即规格驱动开发。

## 这些方法从哪里来，又分别管什么

### 这些名词不在同一层

| 名词 | 它是什么 | 主要回答的问题 | 不应被误解成什么 |
| --- | --- | --- | --- |
| GPT-3.5、GPT-4、推理模型 | 具有不同能力的模型 | 模型能理解、生成和推理到什么程度 | 一个完整业务系统 |
| ChatGPT | 以模型为基础的对话产品 | 人如何方便地使用模型 | GPT 模型版本号本身 |
| Prompt Engineering | 任务指令与示例的设计方法 | 这次到底要模型做什么 | 改写模型权重 |
| CoT | 中间推理步骤及相关提示、训练方法 | 怎样分解多步问题 | 正确性证明或真实思维的完整记录 |
| RAG | 检索与生成组合的系统方法 | 回答需要哪些外部证据 | 把资料永久训练进模型 |
| Tool Calling | 模型提出结构化工具调用的能力和接口 | 如何把语言意图交给程序执行 | 自动获得业务权限 |
| Agent | 根据目标和环境反馈选择行动的系统 | 接下来做什么、是否继续 | 只要套了一个循环就是可靠智能体 |
| Context Engineering | 每轮可见信息的组织与管理 | 当前该给模型看什么 | 把所有资料塞满上下文 |
| SDD | 用规格约束实现和验收的开发方法 | 什么才算把软件做对 | 一代新模型或一次写完的需求文档 |
| Harness | 承载 Agent 的执行、状态、约束和验证环境 | 怎样让任务持续、可控、可恢复地完成 | 单独一条系统提示词 |

Agent、Harness 的边界在不同团队中略有差异。本文把模型驱动的行动决策称为 Agent，把它周围的调度、状态、工具、验证等支撑系统称为 Harness。这是便于工程讨论的工作定义，不宣称是唯一行业标准。

CoT 和 ReAct 的论文都早于 ChatGPT 发布，Prompt 和 RAG 的历史也更早，具体日期见文末原始资料。“ChatGPT → Prompt → CoT → Agent”更像许多人的接触顺序，不能直接当作技术发明的顺序。

模型本身也在变化。预训练打下语言与知识基础，指令微调和偏好对齐让模型更能按要求回答，推理训练则加强多步求解。多模态、工具和运行环境继续扩展它能处理的任务。这些能力往往同时出现在一个产品里。

## ChatGPT 能听懂请求，Prompt 把任务说清楚

### GPT-3.5 与早期 ChatGPT

语言模型的基础训练目标可以直观理解为：给定前面的 token，预测后面的 token。通过大规模数据训练，模型获得语言模式、知识关联以及部分可迁移的任务能力。推理时根据上下文生成内容，普通对话不会自动把用户输入写入模型权重。

GPT-3 的论文展示了通过上下文中的少量示例适配任务的能力。这里的 few-shot 是“把示例放进输入”，与“用几条数据训练一次模型”不同；上下文学习发生在当前推理过程中。[GPT-3 论文](https://arxiv.org/abs/2005.14165)

ChatGPT 的关键推进是对话式产品和后训练的结合。官方首发说明介绍了对话监督微调、人类对候选回答排序、奖励模型与强化学习的流程，并明确它从 GPT-3.5 系列模型微调而来。它因此更适合接受指令和连续追问，但仍可能给出听起来合理的错误答案。[ChatGPT 首发说明](https://openai.com/index/chatgpt/)

以门店客服为例，原来需要专门搭建意图分类器、模板和规则，才能回答一部分问题；对话模型则可以直接理解“昨天点的外卖少了一份菜，怎么处理”。它降低了自然语言入口的开发门槛，但此时还不知道这笔订单是否存在、是否已经退款。

### 退款建议需要怎样的 Prompt

Prompt 是进入模型的指令、问题、示例等输入。在一个应用里，稳定规则、当前任务、检索资料和工具返回通常来自不同位置。好的提示设计首先解决语义问题：目标是什么，已知事实是什么，输出交给谁，缺信息时怎么办。

例如下面是一个用于教学的退款初判模板：

```text
任务：根据提供的订单事实和退款政策，生成客服处理建议。
事实：只使用 orders 数据与 policy 文档，不推测未提供的信息。
判断：核对商品、实付金额、已退款金额、政策版本。
缺失：关键字段缺失时返回 needs_information，并列出缺少的字段。
输出：decision、reason、evidence_ids、missing_fields。
边界：本步骤只生成建议；实际退款由后续业务接口处理。
```

“你是一名资深客服”可以提供角色背景，但不能替代这些约束。相比修饰身份，明确输入字段、处理规则和反例，通常更容易定位输出为什么不符合要求。是否提升效果，应在同一批测试问题上比较，而不是凭某次对话感觉判断。

提示词需要记录版本，传入的数据也要带上结构和来源标识。如果结果还要交给程序处理，程序就得解析并校验字段和枚举。能解析成 JSON 只过了第一关，字段值仍然可能不符合业务要求。

### 改提示词也解决不了的事

Prompt 适合低成本调整任务定义、表达风格、分类标签和输出结构。它的边界也明确：没有订单事实就无法核对订单，没有支付接口就无法退款，没有权限校验就无法保护数据。

同样，网页或文档中的“忽略之前指令”属于不可信内容。仅在提示词里写“不要被攻击”不能建立可靠隔离；外部内容应被当作资料，工具权限和危险操作约束还要在执行端落实。

可以用四个指标衡量这一层：任务准确率、格式合格率、缺信息时的正确追问率、输入变化后的稳定性。若错误来自事实缺失，应改数据链路；若来自规则含糊，应改任务定义；若来自能力不足，再比较模型或训练方法。

## 金额怎么算：CoT 与推理模型

### CoT 为什么会有用

Chain-of-Thought 通常译为思维链。经典 CoT prompting 在示例中加入中间推导，让模型按类似方式处理新问题；Zero-shot CoT 则研究没有示例时，用引导分步求解的提示改善表现。这些研究在特定推理基准上取得提升，不能据此推断所有任务都会变好。[CoT 论文](https://arxiv.org/abs/2201.11903)、[Zero-shot CoT 论文](https://arxiv.org/abs/2205.11916)

教学场景中，一份菜原价 30 元，整单优惠分摊后该菜实付 24 元，之前已经退过 6 元。正确的剩余可退款金额是 18 元。直接问“退多少”，模型可能抓住最显眼的 30 元；要求核对实付、历史退款、可退余额，有助于把多个条件展开。

这个例子需要逐项核对输入，再计算余额。算术结果可以交给确定性函数计算，展示给客服的则是“实付 24 元，已退 6 元，剩余 18 元”这一段可核对的依据。业务并不需要取得模型内部完整的隐藏推理过程。

### 为什么写得更长仍可能错

分步文字可能把错误前提一路放大。若模型误把“原价”当“实付”，后面每一步都能写得流畅，最后仍然多退款。解释的连贯性和答案的正确性是两种不同属性。

因此，推理任务需要外部判定标准：数学题看最终结果与约束，代码任务看测试及真实行为，退款任务看账务和政策。让模型重复自我检查有时有帮助，但多个检查回合可能共享同一个错误假设。

CoT 还增加输出或内部推理的计算开销。简单分类、固定字段抽取未必值得长推理；复杂约束求解才更可能受益。应观察同一任务集上的质量、延迟和成本变化，不把“想得久”直接当作“效果好”。

### 从提示技巧到模型后训练

2024 年 9 月的 o1 代表了一个清晰变化：通过训练强化推理行为，并在作答前投入更多计算。OpenAI 展示了其效果随训练与推理计算增加而改善的实验。这与只给普通模型加一句“分步思考”不是同一个机制。[Learning to reason with LLMs](https://openai.com/index/learning-to-reason-with-llms/)

2025 年的 DeepSeek-R1 论文则区分了 R1-Zero 与 R1。前者探索不以监督微调为前置阶段的大规模强化学习，后者加入冷启动数据和多阶段训练，以改善可读性等问题；论文还展示了向更小模型蒸馏的路径。不能把整条路线压缩成“R1 完全不需要监督数据”。[DeepSeek-R1 论文](https://arxiv.org/abs/2501.12948)

预训练、SFT、偏好优化或强化学习、蒸馏各有作用。预训练建立基础分布，SFT 学习示范行为，强化学习根据奖励调整策略，蒸馏把强模型产生的能力表现迁移给学生模型。奖励容易验证的任务更便于训练闭环，但“奖励高”仍取决于评价标准是否真正代表目标。

推理模型与 Agent 的区别也由此清楚：推理模型可以在一次调用里做复杂求解；Agent 则可能调用模型和工具很多次，根据新的外部反馈改变行动。强推理可以帮助 Agent 决策，却不能替代订单数据库、任务状态或支付系统。

### 照片、语音和更快的响应

GPT-4 在 2023 年强化了通用任务能力，GPT-4o 在 2024 年进一步推动文本、视觉、音频相关的交互。它们是代表性节点，而不是这几年全部能力变化。[GPT-4 发布](https://openai.com/index/gpt-4/)、[GPT-4o 发布](https://openai.com/index/hello-gpt-4o/)

在退款场景里，多模态使系统能够处理缺菜照片、纸质小票和语音描述，但照片是否对应这笔订单、是否重复使用，仍需要业务证据。更长上下文有助于容纳材料，更快推理有助于交互，更小模型有助于成本控制；这些变化都会影响产品设计，不能只用推理能力衡量。

## 查政策、取订单，再决定下一步

### RAG 找政策，业务接口查订单

RAG 将检索与生成结合。经典论文在 2020 年已经提出相关方法；今天工程中更宽泛地用 RAG 指先取出相关材料，再让模型基于材料回答。[RAG 论文](https://arxiv.org/abs/2005.11401)

退款助手要知道门店政策，就应读取适用版本；要知道订单实付，就应查询订单服务。文档检索擅长政策和说明，结构化业务查询擅长实时状态。把订单表全部向量化，并不能自动获得金额计算和事务一致性。

一个可落地的读取链路是：服务端确认身份和门店范围，先过滤允许访问的数据，再检索相关政策，保留版本和条款标识，最后将订单事实与证据交给模型。检索效果与回答效果要分开测，否则无法知道是没找到资料，还是找到了却解释错了。

常见失败有三种：召回了错误门店的规则、找到旧版政策、模型回答超出了证据。分别对应授权过滤、版本管理、引用与忠实度检查。RAG 能减少部分事实缺失，但错误资料同样会使模型更有把握地答错。

### Tool Calling 把语言接到程序

2023 年 6 月，OpenAI 公布 function calling 接口，允许通过函数描述和 JSON Schema 引导模型生成结构化调用参数。这使程序接入不必依赖脆弱的自由文本匹配，但具体函数仍由应用执行。[Function calling 公告](https://openai.com/index/function-calling-and-other-api-updates/)

例如模型提出 `get_order(order_id)`，服务端验证订单属于当前账号后查询，再把结果返回模型。模型负责提出调用，工具适配器负责参数与错误转换，业务服务负责权限和数据约束。不能把模型自行填写的 tenant_id 当作可信身份。

读工具和写工具的后果不同。查询超时通常可以有界重试；退款超时可能意味着钱已经退了但响应丢失。此时应按原请求标识查询处理状态，再决定下一步，不能直接换一个请求号重退。

MCP 在 2024 年 11 月发布，提供 AI 应用接入工具和数据的通用协议。它解决接入方式的复用问题；权限策略、退款规则和跨服务一致性仍要由具体实现负责。MCP 也不是 Agent 必须采用的唯一接入方式。[MCP 发布说明](https://www.anthropic.com/news/model-context-protocol)

### Agent 根据查询结果调整行动

ReAct 把推理与行动交错组织：模型根据当前信息选择行动，读取环境返回，再继续决策。它展示了语言推理与外部交互结合的路径。[ReAct 论文](https://arxiv.org/abs/2210.03629)

在退款案例里，系统先取订单，发现已部分退款，就调整后续金额；发现没有签收或缺失关键凭证，就补充查询或请求人工处理。下一步依赖观察结果，而非只执行预先写死的一串文案。

固定工作流由程序规定主要分支，Agent 在一定范围内自行选择工具与顺序。两者可以组合：让 Agent 收集事实、解释差异，让确定性工作流执行退款状态转换。Anthropic 的工程文章也强调区分预定义工作流与模型动态控制行动的 Agent，并从简单方案开始。[Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)

一个教学性执行循环如下。它强调控制职责，不是可直接投入生产的完整代码：

```text
接收目标，建立 task_id 和可信身份
循环，直到成功、失败、等待人工或达到预算：
    读取任务状态，选择当前必要上下文
    模型提出下一行动或最终答复
    若为工具调用：
        执行端校验权限、参数、风险和业务前置条件
        持久化行动意图，附带稳定的操作标识
        执行工具，记录结果或“结果未知”
        将可核验观察写回任务状态
    若声称完成：
        使用外部结果或验收规则核对目标
        有证据则结束，否则继续或报告阻塞
```

多 Agent 只是对这一体系增加协作分工。独立资料收集可以并行，同一订单的写操作仍需要一致性控制。代理更多会增加重复上下文、通信成本和合并冲突；没有互不依赖的工作包时，一个 Agent 往往更容易管理。

## 资料越来越多，需求也要写清楚

### 这一轮该给模型看什么

当工具、文档和会话不断增多，瓶颈会从提示词措辞转向信息选择。Context Engineering 管理模型当前可见的指令、资料、工具说明、历史和状态，让任务相关证据占据有限注意力。Anthropic 在 2025 年的专文讨论了压缩、结构化笔记和多代理等做法。[Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

一个退款任务可能只需要当前订单、有效政策片段、此前退款记录和待处理事项。完整聊天日志中的寒暄、其他门店案例和数万行工具输出，反而可能遮住关键字段。

这些信息可以分开存放：稳定规则记录版本，当前证据按需获取并附上来源，执行状态单独保存为结构化记录。会话摘要帮助模型接着工作，核对退款时仍要查支付流水。

压缩时要保留尚未完成的目标、关键限制、已执行的写操作、结果未知的操作和证据地址。不能只留下“已经基本完成退款”这种语义摘要。否则新一轮上下文看似完整，实际上丢掉了最关键的副作用状态。

长期记忆还涉及作用域和失效：个人偏好可以跨会话复用，某笔订单的退款资格不能永久复用；缓存键应包含必要的租户、权限和版本信息。内容越多，越需要明确谁能看、何时有效、如何更正。

### 用 SDD 写清退款系统的行为

SDD 在这里是规格驱动开发：先将意图整理成可维护的行为规格，再据此设计、拆任务、实现和验收。规格驱动思想早已存在，2025 年的 Kiro、GitHub Spec Kit 等工具使其更明确地进入 AI 编程流程；并不是那一年才首次有人写规格。[Kiro Spec 文档](https://kiro.dev/docs/specs/)、[GitHub Spec Kit](https://github.com/github/spec-kit)

SDD 与 Agent 有一个层次差异。退款 Agent 是业务系统中的执行者；SDD 则可以用于开发这个退款系统，让编码 Agent 知道哪些行为必须实现。规格也可以成为运行时校验规则的依据，但“开发规格”和“每次运行的任务状态”仍应分开维护。

一句“支持自动退款”不足以写出正确系统。它没有说谁能退、退多少、重复点击如何处理、支付超时怎么办。模型可能自行补齐假设，并写出语法正确、业务错误的代码。

可以先写一份最小行为规格：

```text
目标：对符合政策的缺菜订单提交退款，并让客服看到可核验结果。

身份：订单必须属于服务端认证得到的当前门店范围。
金额：退款额不得超过商品实付减去累计已退金额。
重复：同一业务退款意图重复提交不得产生第二笔退款。
未知：支付调用超时后进入 pending_confirmation，不宣称失败或成功。
恢复：查询原操作状态；确认已成功后更新本地状态。
完成：仅在取得支付结果凭据后显示“退款成功”。

验收示例：
- 实付 24 元，已退 6 元，本次最多申请 18 元。
- 同一操作标识提交两次，只出现一笔支付退款记录。
- 返回超时时页面显示待确认，恢复后与支付结果一致。
- 其他门店订单无法读取，也无法退款。
```

这些条目可以映射为接口约束、数据库约束、状态机和测试。一条退款规则对应哪些代码、由哪个测试检查，最好能查得到。以后修改政策，也就知道要同步改哪些地方。

### 规格需要更新，也需要独立验证

规格不是写完就冻结的长文。需求变化时应更新受影响的行为、迁移策略和验收，保留变更理由；不清楚的产品选择应显式标记，避免让编码 Agent 默默决定。

另一种失败是让同一个模型写规格、写实现、再写只复述实现的测试。三个产物可能共同遗漏同一边界。测试应从业务不变量、事故样本和外部结果出发，而不是仅证明函数返回了预期字符串。

文档写到多细，要看改动影响多大。调整一段文案，目标和截图验收可能就够了。涉及支付、库存、订单的变更，则值得把规格和失败路径写全，否则遗漏往往要到联调甚至上线后才会暴露。

Prompt 表达当前任务，Context Engineering 选择当下信息，SDD 维护预期行为。这三层可以互相引用，但不能相互替代：文档齐全不代表被正确加载，被加载也不代表实现已经通过验收。

## 进程中断以后，Harness 怎样接着处理

### 从一次调用到可恢复的运行环境

Harness 可以理解为模型与真实任务之间的支撑环境。最小实现可能只是一个受控工具循环；生产实现还涉及任务状态、权限、执行隔离、预算、观察、恢复和验收。Agent 靠它取得资料、执行动作，出了错也靠它限制影响范围。

Anthropic 的长任务实践讨论了初始化环境、增量推进和跨上下文窗口留下可接续记录。OpenAI 在 2026 年的实践则强调仓库知识、可观察环境与机械化检查。这些案例为 Harness 提供了具体工程参照，不代表采用相同目录就能获得同样效果。[长任务 Harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)、[Harness Engineering](https://openai.com/index/harness-engineering/)

下面的分解是本文针对业务 Agent 给出的工程设计框架，不是某一家产品的固定内部架构。

| 模块 | 应承担的职责 | 退款案例中的具体表现 |
| --- | --- | --- |
| 任务入口 | 目标、身份、范围、优先级 | 确认处理哪笔订单以及请求人的权限 |
| 上下文组装 | 检索、裁剪、版本与来源 | 只提供当前订单和适用政策 |
| 行动循环 | 工具选择、停止条件、错误分流 | 缺事实先查，结果未知先核对 |
| 工具执行层 | 参数、权限、隔离、限流 | 金额合法且身份符合才允许调用 |
| 状态与事件存储 | 记录意图、尝试、观察、阶段 | 重启后仍知道退款调用是否待确认 |
| 验证器 | 判断目标是否实际达成 | 核对支付流水和页面状态 |
| 预算与调度 | 限制轮次、时长、成本、并发 | 防止同一错误反复调用 |
| 观测与治理 | 日志、追踪、版本、故障归因 | 区分推理错误与支付接口故障 |

### 状态持久化不能只靠聊天历史

假设支付服务已完成退款，Agent 所在进程却在收到响应前崩溃。如果重启后只读到“我准备退款”，就可能重复提交。若读到一句“退款应该完成了”，又可能错误报成功。

应保存结构化操作记录，例如 task_id、operation_id、目标订单、请求参数摘要、状态、尝试次数、外部交易号和最后核验时间。业务服务还需要自己的幂等约束；本地记录不能消除跨网络调用的不确定性。

可将操作状态设计为“待执行 → 执行中 → 成功 / 明确失败 / 结果未知”。结果未知不是明确失败。恢复流程要查询原操作，或通过受控对账消除歧义；外部服务不提供幂等和查询能力时，就必须保留人工核验路径。

这也是 Harness 与“聊天重新连接”的差别。界面恢复历史消息，只证明展示层恢复；任务是否续跑、工具是否重复执行、外部副作用是否一致，都需要单独设计和验证。

### 权限和金额由程序把关

“不要跨门店退款”需要业务服务验证订单归属；“退款不能超额”需要金额约束和并发控制；“运行不能无限花钱”需要预算计数器与停止机制。提示词可以说明规则，但最终约束应落在程序能够拒绝动作的位置。

审批也应绑定具体动作参数及其有效状态。若获批时金额是 18 元，执行时变成 24 元，旧审批就不应继续适用。等待审批期间订单状态发生变化，执行前仍需重新核验业务前置条件。

对于编码 Agent，类似职责体现为工作目录隔离、文件所有权、受控命令、构建环境和版本控制。代码补丁、测试通过、已部署、用户实际可用，是不同层次的证据，不能只用“任务完成”一句话把它们合并。

### 退款成功，要查到交易记录

如果模型说“退款成功”，但没有交易记录，Harness 不应把任务标成成功。如果编码 Agent 说“修好了”，但新进程仍执行旧版本，系统同样不能认为已交付。

验证器可以由断言、状态查询、集成测试、浏览器操作或人工检查组成。模型适合检查语言质量和复杂语义；金额、唯一性和权限等可确定的条件，优先使用程序检查。

设计验证也要防止测错对象：测试环境成功不证明生产成功，某个账号成功不证明租户隔离，HTTP 200 不证明返回的业务数据正确。每个验收项都要明确对象、版本、环境和证据。

### 为什么模型变强后 Harness 仍然重要

更强的模型会降低某些补偿逻辑的价值。例如工具选择变稳定后，可能不再需要复杂的提示路由；代码理解更强后，可以减少机械的文件切分。但身份、权限、交易一致性和审计记录不会因语言能力提升而消失。

升级模型后，可以用固定任务集重新检查这些补偿逻辑，删掉已经没用的部分，再做回归验证。过去为一次失败加上的规则未必需要永久保留，但金额上限、身份校验这类业务约束仍要执行。

## 把这些方法放回同一笔退款

### 同一个请求在不同阶段能走多远

用户说：“昨天订单少了一份菜，帮我处理退款。”从理解这句话到完成退款，各种方法能补上的能力如下。

| 体系 | 能做到的事 | 仍然缺失的条件 |
| --- | --- | --- |
| 对话模型 | 理解抱怨并生成回复 | 没有订单事实 |
| 加 Prompt | 按固定格式追问订单号 | 无法验证用户陈述 |
| 加 CoT 或推理能力 | 分解金额与规则判断 | 缺少可核实输入时仍可能算错 |
| 加 RAG 与查询工具 | 找政策、查实付和历史退款 | 尚未形成受控写入流程 |
| 加 Agent | 根据查询结果决定后续步骤 | 进程失败、越权和重复写入仍需处理 |
| 用 SDD 开发 | 明确各状态行为和验收标准 | 规格还需要被实现和持续验证 |
| 加完整 Harness | 受控执行、恢复、核对结果和记录证据 | 仍受模型、数据及外部业务系统能力限制 |

实际系统里，SDD 主要发生在开发和变更阶段；运行时由 Context Engineering、Agent Loop、工具服务和 Harness 共同配合。不要把这张表理解成每次退款都要现场写一遍开发规格。

### 一条完整的请求链

1. 用户提交问题，应用从登录态取得可信身份，建立任务标识。
2. 系统查询授权范围内的订单与适用政策，保留证据版本。
3. 模型识别缺失事实并提出必要查询，程序校验每次调用。
4. 确定性逻辑计算可退金额，Agent 解释依据；如需审批，绑定具体操作。
5. 执行端使用稳定操作标识提交退款，并持久化尝试与结果。
6. 如果调用超时，进入待确认状态，查询原操作而非盲目重复写。
7. 验证器核对支付结果与本地状态，确认后向用户报告完成。
8. 记录版本、耗时、成本与失败类别，为后续模型和系统迭代提供样本。

这条流程把语言理解和信息整合交给模型，把精确计算、状态和事务留给程序。这样排查错误时也容易定位：是政策理解错了，还是退款接口没有按约定执行。

### 评价对象要从答案扩大到完整任务

单轮准确率无法代表长任务成功率。举一个数学上的简化例子：若每一步条件成功率均为 95%，完成十步的概率为 0.95 的十次方，约 59.9%。这不是任何产品的实测数据；实际错误还可能相关，恢复机制也会改变结果。

可建立一份分层指标表，避免只盯着模型分数：

| 层次 | 主要指标 | 指标异常时先查什么 |
| --- | --- | --- |
| Prompt / 输出 | 正确率、结构合格率、必要追问率 | 任务定义、示例和字段约束 |
| 推理 | 最终结果正确率、约束满足率、推理耗时 | 输入完整性、求解难度、验证方法 |
| 检索 / 上下文 | 证据召回、版本正确性、引用支持率 | 授权过滤、索引、裁剪和过期内容 |
| 工具 | 参数有效率、业务成功率、未知结果占比 | Schema、权限、接口和网络 |
| Agent / Harness | 端到端成功率、恢复率、越权和重复副作用 | 状态机、幂等、预算、验证器 |
| 产品 | 人工接管率、P95 延迟、每个成功任务总成本 | 整条任务链，而非单次 token 单价 |

每个成功任务总成本，可以用一段时间内模型、工具、基础设施及人工处理的总成本，除以成功任务数估算。便宜模型反复失败可能更贵；昂贵模型被用于简单分类也可能浪费。需要在同一任务分布上比较。

评测集应包含正常任务、信息缺失、政策冲突、越权访问、重复提交、工具超时和中断恢复。固定测试集用于回归，再用新的真实失败样本补充，避免提示词只针对已见题优化。

### 遇到什么问题，就补哪部分能力

如果只是固定分类，先尝试单次模型调用和结构校验。如果事实来自内部文档，补检索。如果过程分支固定，用工作流。如果需要根据新证据动态决定步骤，再引入 Agent。如果工作跨会话、有副作用、需要可靠恢复，就明确设计 Harness。

开发需求本身含糊、变更影响多个模块时，补 SDD；当前轮次总是遗漏相关资料时，补上下文工程。微调适合改善稳定、重复的行为模式，不应被当作更新实时订单事实的替代品。

做一个小项目就能检验这些选择。起初只用固定订单生成处理建议，随后加入政策检索、只读查询和工具循环。等到真正接入退款，再补齐状态、幂等和中断恢复，并用故障演练检查它们是否起作用。

回到最初那句话，系统是否完成任务，最终要看这笔钱有没有退对、客服能否查到结果。Prompt 写得清楚，推理过程合理，工具调用成功，都只是中间步骤。遇到支付超时还能查回原交易，重启后也不会再退一笔，才说明支撑这个助手的软件把事情接住了。
